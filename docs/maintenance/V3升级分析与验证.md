## 结论与升级方式

可以升级，已在当前目录完成增量整合。V3 与当前库是分别演进的两个分支，不能直接用 V3 覆盖整个目录：V3 强化了生成质量、覆盖数量和资源核算；当前库已有 Excel 规范化、人工准备分流和原始用例结果聚合。此次升级把两组能力合并，并修复了来源兼容、报告固定描述和文档冲突。

## 架构判断

框架的核心是“技能路由 + 结构化契约 + 确定性门禁 + 执行器 + 交付生成器”，不只是 Playwright 测试脚本集合。

```mermaid
flowchart LR
    A[用户 PRD 或已有 Excel] --> B[来源条款与原子规则]
    B --> C[覆盖义务与测试点]
    C --> D[唯一最终用例与设计门禁]
    D --> E[人工准备与执行计划门禁]
    E --> F[pytest / Playwright 与逐次证据]
    F --> G[执行门禁与 Excel 回填]
    G --> H[交付门禁与 Word 报告]
    M[工作流时长与 Token 账本] -.-> E
    M -.-> F
    M -.-> H
```

`SKILL.md` 决定阶段入口和停止条件，`references/` 说明业务设计与执行规则，`assets/templates/` 定义产物形状，`references/scripts/` 验证跨文件关系并生成交付物。`builtin_framework/` 承担可重复的浏览器执行。唯一执行来源仍是 `06_final_test_cases.yaml`。

## 合并时修复的问题

1. **XLSX-only 与 PRD 来源冲突。** V3 原门禁强制 `current_prd_only`。现支持规范化模式的 `current_xlsx_baseline`：来源文档必须声明 `existing_xlsx_baseline`，SHA-256 必须匹配导入账本，条款和规则必须引用真实工作表与源行。最终源仍声明 `requirement_completeness: not_assessed`。覆盖下限是 Excel 基线事实的设计下限，不代表完整需求覆盖。
2. **权限事实被静默遗漏。** V3 权限计算只采用 operations、data_scopes、outcomes 的第一个值。现要求每条权限原子规则分别只有一个操作、数据范围和结果，多事实需要拆规则，避免丢失事实或无依据的笛卡尔膨胀。
3. **缺少前置数据仍可能填写 passed。** 现强制环境提供或系统预置的前置数据缺失处理必须为 `blocked`，不能只填任意非空文本。
4. **确认时间验证不完整。** 改为真实 ISO 8601 日期解析，接受时区，拒绝不存在的日期。模板中的确认人、日期和评分仅是格式示例，项目使用时必须真实确认与评审。确认字段存在和日期有效仅证明记录格式，不证明业务人员确实确认。
5. **迁移辅助工具猜测字段。** 未明确的前置来源不再默认 environment_provided，不再虚构 PRD-001，不再把模块名当作步骤目标。迁移报告要求补充缺口，并提醒从既有规则派生的条款账本仍需回比原文。
6. **smoke 标签可绕过生成契约。** 生成/评审模式只接受 full、generation_review 和显式 l2_only。缩小执行范围不等于可以把完整生成产物伪装成 smoke 来关闭质量契约。
7. **报告与账本不一致。** 移除固定“无正式 PRD”“营销路由”“会话复用”等描述；来源不明时明确写未声明。最终账本在交付门禁后变化时，正式报告生成会被拒绝。执行门禁时账本可仍在记录后续交付阶段，报告因此以最终交付门禁绑定的快照为准。
8. **覆盖数量和范围冲突。** 新质量契约以独立 N_min 和必要签名为准，移除强制用例数大于需求数的旧要求；单一规则可有一条用例。risk-first 不强制凑齐三级，缺档必须逐档说明风险事实。显式 l2_only 现在三处声明一致后可真正通过限定范围门禁，且报告披露其不代表全量覆盖。存量审计不因已声明但未补齐的数量契约而误阻断，仍不代表质量契约合规。
9. **模板与提示词冲突。** 同步默认 10 列（含执行级别、人工介入说明、人工准备清单）、按风险判级、生成阶段不伪造环境探测、独立试点与正式稳定排序规则，并修正发布检查单的旧绝对路径和 cmd/PowerShell 混用。

## 新项目与存量项目怎么使用

- **新 PRD 项目：** requirements 顶层和 case_source 同时声明 `quality_contract_version: "1.0"`，保留原子契约版本；先形成条款、事实、规则和覆盖义务，再生成用例与独立评审。新计划和执行/交付校验都加 `--require-resource-accounting`。
- **已有 Excel、没有 PRD：** 先运行 import_existing_cases.py；用 `current_xlsx_baseline` 和 `supplied_baseline_only`，绑定账本哈希、sheet、row；补足用例契约和真实评审，继续走同一设计门禁。无法证实的业务预期不能猜测。
- **已有 Excel、同时提供 PRD：** PRD 作为业务事实来源，使用 `current_prd_only`；用户提供的 Excel 可作为可复用资产，保留 normalization_trace 并处理冲突。
- **历史 YAML：** 可先用 `--legacy-audit` 获取迁移差距；它仍检查基础原子账本、来源、执行语义等，不保证任何旧文件都能直接通过。兼容通过会标记 quality_contract.enforced=false；补齐后必须去掉开关重新验证。正式报告会披露存量兼容审计。
- **工作流账本：** 真实 usage 可取得时才登记 exact；只取得部分时登记 partial；宿主未暴露 usage 时登记 unavailable；全确定性运行可登记 not_applicable。不可用不等于零，也不以估算冒充实耗。冻结最终账本；若核算状态或引用元数据变化，更新结果并重新跑执行门禁和回填；然后重跑交付门禁，再生成正式报告。

## 仍需认清的边界

机器门禁能检查声明、映射、计数、哈希和证据形状，不能证明所有 PRD 条款已被提取，也不能仅凭评分说明证明评审独立或截图中业务判断真实。语义重复检查依赖声明的 semantic_identity 与文本规范化，不是任意改写的完整语义判重。PRD 扫描器仍可能误报和漏报，原文章节回比、真实独立评审、关键证据复核和 P0 阻塞签核仍需要执行人员完成。

资源账本使用单文件更新，未引入多进程锁；同一项目不要并发写同一账本。runner 的账本写入异常会告警，正式资源核算门禁会拒绝缺失或无效账本，不能将 runner 已完成测试等同于正式交付合规。

当前 validate_case_design.py 已较大。本次优先保持升级兼容性；后续可在行为测试保护下按来源契约、覆盖计算、评审和排序拆分模块，而不同时改动产物字段。
