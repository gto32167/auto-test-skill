# AI 测试工作流试点介绍（归档）

> 本文件是汇报材料，不是工作流规范。规则、能力和验证数字可能随版本变化；实际执行必须以 `SKILL.md`、`references/` 和当次门禁结果为准。

## 方案定位

输入当前项目 PRD 和环境信息，形成“需求拆解、用例设计、评审、执行、回填、正式报告”的测试交付链。目标不是代替人工缺陷确认，而是让 AI 产生可复审、可追溯的测试事实。

## 主要能力

- 需求、测试点和最终用例一对一闭合。
- 11 维评审和 P0/P1/P2 专项门禁。
- 确定性脚本、Playwright MCP 和 API 辅助三类执行通道。
- 语义契约、逐 attempt observations 和防假阳性判定。
- 重试 3.0、passed/failed/blocked 三态和独立复核。
- 前置数据独立构造和业务数据回填。
- UI 文件哈希与语义 manifest、API 独立证据引用。
- 回填版 Excel、Markdown 审计源和 Word 正式报告。

## 质量边界

- 自动化观察不等于已确认缺陷，疑似问题仍需产品或开发确认。
- UI 复杂交互、验证码、外部物流和人工审批可能造成阻塞。
- PRD 歧义会直接限制用例和结论质量。
- 结构化证据可以发现版本和内容矛盾，但不能单独抵御执行器同时伪造全部事实。
- 高风险通过项仍需要人工抽样或独立通道复核。

## 推广建议

先在核心主流程和规则类场景落地，记录实际范围、执行预算、稳定性、阻塞归因和缺陷确认结果，再扩展到相邻模块。每轮只把跨项目有效的经验回写到 `execution-playbook.md`，项目专属端点和选择器留在项目目录。

历史升级和回归数据见 `docs/history/CHANGELOG_202608.md`。
