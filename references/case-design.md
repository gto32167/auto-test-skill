# 用例设计方法

## 执行分级与人工准备

每条最终用例增加 `execution_readiness`，与 P0/P1/P2 业务优先级、L2/L3 覆盖粒度独立：`auto` 可自动执行，`assisted` 需人工准备后自动执行，`manual` 核心操作必须人工执行。交易、付款、支付、扫码操作必须列入 manual；复杂前置中的人工数据、权限、配置必须逐项写清内容、负责人和验收条件。用例表在优先级之后显示“执行级别、人工介入说明、人工准备清单”。缺少分级不能通过设计门禁。完整字段与示例见 [human-readiness.md](human-readiness.md)。

独立性要求每条用例拥有独立前置数据；自动无法造数时允许人独立准备并确认，禁止依赖其他用例执行成功。评审阶段必须发现并提示已知人工依赖，不能等到开始执行才报前置缺失。

## 目标

输出既符合表格化交付规范、又尽可能可执行的测试用例，让测试人员、AI 或自动化工程师都能直接复用。

## 前置约束

正式生成用例前，必须先读取：

- 用例编写规范
- 用例模板
- 原始 PRD 或原型图

如果规范、模板或 PRD 任一缺失，应先记录风险或阻塞，而不是直接自由发挥。

## 用例独立性硬规则

用例必须可独立执行，不依赖其他用例的执行结果。评审时违反以下任一条即一票否决：

1. 禁止以“TC-XXX 执行结果”“复用上一用例产出”作为前置条件
2. 前置条件必须可自行满足；前置写清需要的业务状态/数据来源，构造动作不写入正式业务步骤，由执行器在执行前按独立 setup strategy 完成
3. 每条用例的测试数据必须带唯一标识（时间戳 / 随机后缀），保证重复执行幂等，不与其他用例数据冲突
4. 执行产生的业务数据（订单号、商品名、退款金额、库存变化等）必须记录为 `produced_*` 字段，供报告回填与断言复用
5. 需要前置业务状态（如“已支付未发货订单”）时，用例自身应声明该状态；具体构造动作由执行器在执行前独立完成，不写入正式业务步骤
6. 前置条件只允许来自当前 PRD、当前项目背景或当前环境探测结果；不得把上一项目的默认资源假设（如图片库、验证码、统一登录方式、共享素材库）直接带入当前项目。对于当前项目未明确的支持资源，不要在正式用例里提前写死“有/没有”，而应把它当成执行阶段需要探测和构造的前置依赖，由 `data_setup` / setup strategy 先尝试满足

独立性带来的收益：任意一条用例可单独重跑；失败用例不阻塞下游；支持并行执行与断点续跑。

## 结构化测试数据契约（2026-09-03）

涉及 Excel/CSV/JSON/表格导入或其他结构化输入的用例必须声明 `fixture_contract`，至少说明：

- 文件格式，以及是否必须使用当前系统下载模板；
- 完整表头、预期缺失表头、列顺序和每行列数约束；
- 需要为空和必须非空的字段；
- 本条用例期望进入的反馈类别（如 `missing_header_validation`、`required_value_validation`、`file_parse_error`）；
- 需要出现在提示中的字段锚点，以及明确排除的其他错误类别。

负向用例只允许改变一个目标变量。表头缺失与字段值为空是两个不同等价类：缺失表头时必须从数据行同步删除该列；字段值为空时必须保留完整表头并只清空目标单元格。禁止用列数不一致、字段错位或自定义占位列代替业务异常数据。

执行器在上传前必须读取并校验 `fixture_contract`：表头与每行列数一致、必填/空值状态正确、缺失字段集合正确。校验失败属于测试数据构造失败，不能进入产品结果统计，也不能被页面的通用解析异常掩盖。评审时应将 fixture 校验视为“数据可执行性”和“业务正确性”的硬门禁。

## 前置条件三态（2026-08-24 新增，一票否决项）

**每条用例的前置条件必须明确标注三态之一，禁止写"存在商品/存在订单"这类无来源声明**：

| 前置态 | 定义 | 写法要求 | 评审判定 |
|--------|------|----------|----------|
| **自造**（推荐） | 用例自己满足所需前置数据 | 前置条件写清"需要什么业务状态/数据"，或写"无（由执行器自造）"；构造策略放在独立 `data_setup`/`setup strategy`，不写入正式业务步骤 | ✅ 通过 |
| **系统预置** | 数据由被测系统/种子数据提供 | 前置条件写"系统预置：XXX（来源/种子文件）"，步骤验证预置数据存在 | ⚠️ 仅限无法自造的只读验证场景 |
| **环境提供** | 数据来自真实历史数据（如生产/存量） | 前置条件写"环境提供：XXX（来源）"，步骤必须含"无则跳过并标记 blocked"的兜底 | ⚠️ 仅限自造成本极高的场景（如长链路历史订单） |

**硬性规则**：
- 前置含"存在X"且步骤无构造段 → 评审"数据可执行性"维度 0 分打回
- **自造优先**：能独立满足的前置就独立满足；执行器可按项目情况选择 API 或 UI 构造前置，商品/分类/标签/下单支付均可由统一构造层处理
- 自造态由执行器按 setup strategy 完成前置构造，造数结果写入 `runtime/<case_id>_data.json` 并回填 produced，但不进入正式业务步骤
- 只有"自造"可独立重跑；"系统预置/环境提供"必须带兜底（数据缺失 → blocked 而非失败，blocker_type=前置缺失）

> 反面示例（禁止）：前置"存在待发包裹订单"，步骤直接"订单号筛选→发货" → 数据从哪来？不可执行。
> 正面示例（推荐）：前置"需要一条已支付未发货订单（由执行器独立构造）"；步骤 1 进入订单列表；步骤 2 按 orderNo 筛选；步骤 3 发货并核对状态。

## 设计方法

本方案默认组合以下方法：

1. 等价类
2. 边界值
3. 判定表
4. 场景法
5. 状态迁移
6. 因果图简化思路
7. 错误推测

## 用例分层

### L1 冒烟用例

- 验证主流程是否可走通
- 数量少，优先级最高
- 适合首轮浏览器执行

### L2 核心业务用例

- 验证关键规则和关键分支
- 覆盖主业务风险

### L3 扩展与异常用例

- 验证边界、异常、权限、回退、兼容性

### 场景用例 与 字段用例 分层

用例按覆盖粒度分为两层，设计时必须区分并标记：

- **场景用例（场景级，默认 L2）**：验证"功能点能不能用"，主流程 + 关键分支 + 关键逆向。用于冒烟 / 回归 / 主链路执行。
- **字段用例（字段级，L3）**：验证"每个字段的每种输入形态"，按下方「字段级覆盖规则」展开。用于全量验证、交付前完整回归。

执行时按需选择层级：

- 冒烟 / 快速回归 → 只跑场景级
- 全量验证 → 场景级 + 字段级

## 字段级覆盖规则（核心表单类功能强制）

针对核心表单类功能（创建/编辑商品、下单、发货、售后处理、用户信息等），字段用例必须覆盖以下各类，缺任一类别视为覆盖不完整：

### 一、输入框

1. 有效数据：中文、英文、数字、组合、特殊字符各至少一条
2. 无效数据：空、空格、超过最大字符数
3. 必填项（带 * 标识）：填写 + 未填写各一条
4. 类型专项：
   - 价格类：有效=正整数、小数点后两位内；无效=空、空格、非数字、负数、超过两位小数、超长
   - 手机号/身份证类：构造非手机号、非身份证格式数据
   - 库存类：无效值必须包含 0
5. 边界值：最小值、最大值、最小-1、最大+1（若长度/范围已知）

### 二、下拉框

1. 逐项选择所有备选项，每项校验列表/详情数据正确性
2. 默认值校验（首次进入时的默认选中项）

### 三、上传文件

1. 图片类：常见格式（jpg/png）+ 非图片格式
2. 文本类：常见格式 + 非文件格式

### 四、复选框 / 多选

1. 选中 / 未选中各一条
2. 存在多个可选项时，构造混选（组合选择）用例

### 五、数据统计

1. 构造数据变动对统计的影响（如订单统计：下单 +1，退款 -1）
2. 统计值可点击跳转明细时，验证跳转正确性

### 六、适用与评审

- 字段级覆盖仅对"核心表单类功能"强制，非表单类（列表、跳转、展示）不强制展开
- 场景用例评审通过后，字段用例按本规则批量补充，无需逐条重复评审业务正确性
- 用例中通过 `level: L2 | L3` 标记层级，执行计划可按 level 过滤

### 七、合法字段值的持久化校验

当用例要证明“系统接受并保存了合法字段值”时，不能只在当前输入框读取刚填入的值。该用例必须声明 `operation_type: persisted_validation`，并完成：填写其他合法必填项、保存或提交、按本轮唯一对象标识重新查询或重新打开同一对象、比较输入值与保存后回显值。

`persistence_verification` 必须将 `required`、`commit_required`、`reopen_or_query_required`、`compare_input_persisted` 设为 `true`。结果契约至少包含 `object_id`、`input_value`、`persisted_value`、`persistence_verified`、`mutation_committed`；修改已有字段的 `operation_type: edit` 还必须包含 `before_value` 并设置 `baseline_required: true`。保存接口成功但未反查，或只截图编辑页而未显示断言字段，均不能判定通过。

### 变化类用例的证据设计（2026-09-02）

编辑、删除、选择/取消选择、重新上传、合并、添加、提交及状态流转等会改变可见页面或业务状态的用例，必须额外声明 `change_evidence`，不能只沿用普通场景的一张结果截图：

```yaml
change_evidence:
  required: true
  change_type: edit           # edit / delete / change / state_transition
  comparison_required: true
  before_assertion: 操作前可定位对象、字段或列表状态
  after_assertion: 操作后同一对象、字段或列表状态
```

其结果契约必须至少能够表达 `before_value`/`after_value`（或 `before_state`/`after_state`）、`changed`、`comparison_verified`。执行时每个 attempt 在变化动作前后各截一张独立截图，截图必须对准断言字段/对象容器；编辑还要显示前值与保存后回显，删除还要显示删除前对象与删除后不可见或数量减少。缺少前后任一证据、对象无法对应或无法证明差异时，评审与执行门禁不得判定为 `passed`。

## 单条用例必须具备的字段

对内结构化字段建议保留：

- `case_id`
- `requirement_ids`
- `module`
- `priority`
- `priority_rationale`
- `level`（L1/L2/L3；L3 需标注场景级还是字段级）
- `preconditions`
- `test_data`
- `steps`
- `assertions`
- `cleanup`
- `automation_candidate`
- `data_setup`（可选）：独立数据准备段，描述本用例所需前置状态及其构造策略（不占用正式业务步骤）
- `api_fallback`（可选）：UI 执行受阻时的 API 直连兜底验证通道

对外最终交付优先转成表格列：

- `用例名称`
- `优先级`
- `前置条件`
- `执行步骤`
- `预期结果`

如果项目已经存在既定 Excel 模板，应优先兼容模板列结构。

### 正式交付用例文本规则

`08_测试用例_模板版.xlsx` 和用户提供模板中的正式用例内容必须按人工评审文档口径输出，不得直接暴露执行器内部字段。

- **全中文交付**：正式列中的用例名称、前置条件、执行步骤、预期结果必须使用中文业务表达。`execution_profile`、`open_url`、`assert_text`、`valid`、`field_id`、`coverage_class` 等英文或自动化字段只能留在 YAML 内部元数据，不得出现在正式 Excel 单元格中。
- **PRD-only 来源**：用例名称、步骤和预期结果只能来自 PRD、原型/截图、用户背景说明或明确的测试设计推导；不得混入历史执行记忆、页面探针结果、接口字段名、执行脚本变量名。代码/API/执行探索只能作为执行定位参考，不能改写正式需求预期。
- **名称与预期职责分离**：用例名称描述“测试什么”（模块 + 场景/字段/规则），预期结果描述“执行后应观察到什么结果”。禁止用例名称和预期结果高度重复。
- **预期结果自包含**：预期结果必须把可判定的业务规则写完整，例如状态、金额、字段回显、提示文案、列表变化、权限拦截结果。禁止写“符合 PRD 约束”“与需求一致”“按规则展示”等需要读者再查第三方资料才能判断的表述。
- **功能集合聚合排序**：最终用例和模板版 Excel 必须按当前 PRD 的功能出现顺序组织，并以端口、页面或相似功能形成可评审的功能集合；同一集合的场景级、字段级、边界/异常用例必须连续，不得先集中列出全部场景级，再把字段级散落到后半段。
- **执行器元数据隔离**：如果需要保留自动化动作、选择器、路由、数据构造策略，应放在 `automation_meta`、`data_setup`、`precondition_data` 或执行计划中；正式 Excel 的“执行步骤”只写用户/测试人员可理解的业务操作。

## 功能集合与排序契约

`feature_group` 是用于编排和评审的结构化字段，表示同一端口下的同一页面、相似功能页面或需要连续评审的功能集合。它比宽泛的 `module` 更具体；例如 `商品管理` 是模块，`供应商端-商品编辑页` 才是功能集合。测试点与其对应的最终用例必须声明完全一致的非空 `feature_group`。

最终用例源必须声明：

```yaml
case_ordering:
  policy: prd_port_page_group
  source: 01_需求原文.docx
  group_sequence:
    - PC商城-常购清单入口与列表
    - PC商城-商品详情页加入常购
```

排序按以下层级确定：

1. 以当前 PRD 正文、目录或原型的首次出现顺序确定业务功能先后，不按编写者想到用例的时间排序。
2. 同一业务功能涉及多个端口时按 PRD 端口出现顺序排列；未给出端口顺序时保持 PRD 原有叙述顺序，不擅自按优先级重排。
3. 同一端口内按页面或相似功能形成 `feature_group`；同页面的展示、查询、编辑、边界和异常用例必须放在一起。
4. 同一集合内部按“入口/主流程 → 展示 → 查询筛选 → 字段/数量 → 删除管理 → 正向操作 → 逆向/边界 → 质量属性”排列，仅保留当前集合适用的阶段。
5. 跨端口的共同规则可放入独立的“通用”集合，但必须在相关端口功能之后出现，并说明为何不能归入单一页面。

同一 `feature_group` 必须在 `test_cases` 中形成一个连续区间，不能被其他集合穿插；实际出现的集合顺序必须与 `case_ordering.group_sequence` 完全一致。`05_test_points.yaml`、`06_final_test_cases.yaml` 和 Excel 的行顺序必须一致。默认 Excel 列为：`用例ID / 功能集合 / 用例名称 / 优先级 / 前置条件 / 执行步骤 / 预期结果`。若用户模板已有等价的模块/页面列，可映射该列，但不得丢失功能集合信息。

## 单用例单验证点原则

- 每一条用例只验证一个点
- 一条用例不得同时验证两个或两个以上功能点
- 如果步骤超过 5 步，优先考虑拆分用例
- 如果预期结果需要覆盖多个彼此独立规则，应拆成多条用例

## 需求 → 测试点 → 用例（用例数必须大于需求数）

**核心约束**：最终用例数必须大于需求条目数。一条需求按测试设计方法可拆出多个测试点，**1 测试点 = 1 用例**，禁止把多个测试点合并进一条用例。

**拆解方法**（每条需求按以下维度展开）：

| 维度 | 说明 | 每条需求至少 |
|------|------|-------------|
| 正向 | 主流程、合法路径 | 1 |
| 逆向 | 必填缺失、非法操作、权限拦截 | 1~2 |
| 边界/非法 | 长度边界（最小/最大/±1）、类型非法（非数字/非手机号）、数值越界（负数/超精度） | 按字段 |
| 分支 | 下拉/radio/checkbox 逐项选择 | 每选项 |
| 状态流转 | 合法流转、非法流转、回退 | 各状态对 |

**核心表单类功能强制字段级展开**（创建/编辑商品、下单、发货、售后、用户信息）：
- 输入框：有效（中文/英文/数字/特殊字符）、无效（空/空格/超长）、必填（填/不填）、类型专项（价格/手机号/库存）、边界值
- 下拉框：逐项选择 + 默认值
- 上传：合法格式 + 非法格式
- 复选框：选中/未选中/混选

**自查标准（用例设计完成前必须满足）**：
- 用例数 > 需求数；具体数量由测试点与字段覆盖类别决定，不使用固定条数或固定倍数替代完整性判断
- 每条用例的"预期结果"只包含一个独立断言目标（若需验证 A、B、C 三个独立结果 → 拆 3 条）
- 场景级用例（L1/L2）保留作为冒烟回归集，字段级用例（L3）补充作为全量验证集，两层都输出
- 正式交付列不得出现执行器英文动作或占位字段；预期结果不得写“符合 PRD/按规则”等非自包含表述

### 字段覆盖清单必须结构化

核心表单字段不能只在评审文字中写“已覆盖”。`05_test_points.yaml` 必须为每个字段声明所需覆盖类别，并由字段测试点逐项满足：

```yaml
field_coverage:
  - field_id: "goods.name"
    required_classes: ["valid", "empty", "whitespace", "max", "max_plus_1"]

test_points:
  - test_point_id: "TP-GOODS-NAME-EMPTY"
    requirement_ids: ["REQ-GOODS-001"]
    granularity: "field"
    field_id: "goods.name"
    coverage_class: "empty"
    polarity: "negative"
    interface: "ui"
    expected_outcome: "rejected"
```

覆盖类别由 PRD 字段类型和约束决定，不使用固定的通用列表强塞到所有字段。输入框、下拉、上传、多选等应按本文件前述字段级规则声明各自 `required_classes`。所有测试点还必须明确 `polarity`、`interface` 和 `expected_outcome`，让正向/负向及“提交成功/被拒绝/只观察状态”的意图可以被机器校验。

## 最终用例唯一来源与机器门禁

- `04_scenario_cases.yaml` 是 L2 初稿，只用于设计和形成回归标签，不得直接作为任何执行源。
- `06_final_test_cases.yaml` 是唯一执行源，必须包含全部场景和字段测试点。
- 每条最终用例必须包含唯一 `test_point_id`、`granularity` 和恰好一个主断言。
- `06_final_test_cases.yaml` 顶层必须用 `executor_profiles` 声明每个 profile 支持的能力和通道；用例的 `execution_profile`、`execution_contract` 必须与其 `test_intent` 匹配。
- `result_contract` 必须使用 `verdict: all` 和结构化 `observations` 声明来源、比较操作、期望值及证据要求；`required_produced_keys` 必须与 observation 键完全一致。
- `assertion_policy` 必须把全部 observation 键完整划分为 `hard_keys` 和 `soft_keys`，每个 observation 同时声明 `assertion_class`。精确 UI 提示文案只有 PRD 有逐字依据并声明 `prd_exact: true` 时才能为 hard，否则必须为 soft。
- `expected_outcome: rejected` 必须同时声明主接口拒绝证据和 `mutation_committed equals false`，仅有提示或仅有“未保存”文字都不够。
- 拒绝类 `mutation_committed` 必须在 `hard_keys`；软提示差异不能覆盖业务写入硬断言。
- 顶层 `review_audit` 必须记录不少于总用例 10% 和 P0 20% 的环境可执行性抽样；每项保留探测通道、证据和修订动作。全部用例 22/22 时必须填写可核查的满分依据。
- 评审评分不能代替机器门禁。生成模板版前必须运行 `references/scripts/validate_case_design.py`；如果本轮继续执行，生成执行计划前也必须先通过该门禁。

门禁最小命令：

```powershell
py references/scripts/validate_case_design.py `
  --requirements <项目目录>/05_requirements.yaml `
  --test-points <项目目录>/05_test_points.yaml `
  --final-cases <项目目录>/06_final_test_cases.yaml `
  --output <项目目录>/07_case_design_gate.json
```

`07_case_design_gate.json` 不是说明文档，而是下游脚本必须校验的授权凭据。门禁记录三份输入的 SHA-256，并为每条用例输出 `semantic_contract_sha256`；通过后修改最终用例会使计划、执行和回填立即失败。完整规则见 [semantic-contract-gates.md](semantic-contract-gates.md) 和 [delivery-gates.md](delivery-gates.md)。

> 反例（禁止）：TC-001 同时断言"创建成功 + 出售中列表 + 类型一致 + 价格一致 + 库存一致 + 推广链接"（6 个验证点）。
> 正例（推荐）：拆成 6 条——创建成功 / 出售中列表可见 / 类型一致 / 价格一致 / 库存一致 / 推广链接生成，每条一个断言目标。

## 断言强度分级

为提升断言可靠性，将断言划分为三级，设计用例时按场景选择：

### 弱断言（仅作冒烟提示，不作为通过依据）

- 页面出现某个关键词即判通过，例如“页面出现‘退款’字样”
- 风险：关键词可能来自菜单、Tab 标签、说明文案，容易误判

### 强断言（默认标准）

- 必须是“状态机 + 可观察证据”的组合：
  - 时间戳型：例如同时出现“商家处理退款申请(时间戳) + 退款完成(时间戳)”
  - 数据对比型：例如库存三段式 `下单前 N → 下单后 N-1 → 退款后 N`（回退即恢复）
  - 金额显式区分：`期望=实付`、`期望=实付-运费`、`期望=商品价+运费` 必须写明公式而非只写数字
- UI 断言优先辅以 API 回显佐证（接口返回 Code=0 + 字段值）

机器契约中的 `hard/soft` 与上面的业务强弱口径对应但不混用：`hard` 决定通过/失败，`soft` 只记录表现差异。提示文案通常为 soft，资金、库存、权限、状态和 `mutation_committed` 等业务不变量通常为 hard；PRD 明确逐字约束的文案可声明 `prd_exact: true` 后作为 hard。

### 阶段断言（仅限长流程闭环用例）

- 对于“申请→处理→寄回→收货→退款”这类多角色长闭环：
  - 允许验证到“当前阶段状态正确”即判定通过
  - 完整闭环单列人工或后续轮次
  - 用例中必须显式标注 `long_flow: true` 与当前验证到的阶段

## AI 可执行增强规则

为了提升 AI 直接执行成功率，增加以下约束：

- 不写“检查是否正常”这类模糊断言
- 不写“正常显示”“无异常”这类模糊预期
- 页面对象尽量提供稳定定位语义，例如按钮文案、字段标签、表格列名
- 步骤里不要混合多个动作，例如“填写并提交并查看结果”
- 前置条件要写成可验证状态，而不是“系统准备完毕”
- 测试数据必须显式给出来源或生成规则
- 预期结果必须能在页面、接口回显、数据库回写或文件产物中观察到至少一种
- 若字段最大长度、最小值等未知，必须显式标注“待确认”，不得自行假设具体值

## 设计顺序

1. 先按 PRD 或原型图拆出功能点
2. 读取编写规范与模板
3. 输出 `05_requirements.yaml`，为每个需求标明 covered / explicitly_not_tested / pending_confirmation
4. 输出 `05_test_points.yaml`，先拆 L2 场景点，再按字段清单补齐 L3 点
5. 生成 `04_scenario_cases.yaml` 场景初稿，但禁止直接用于执行
6. 按“1测试点=1用例”生成 `06_final_test_cases.yaml`
7. 建立 `case_ordering.group_sequence`，按 PRD、端口和页面/相似功能集合重排测试点与最终用例，确认每个集合连续
8. 将最终用例与 PRD 逐条核对并完成 11 维评审
9. 运行用例设计门禁；失败则回到测试点或最终用例修订
10. 门禁通过后先输出表格版本；如果本轮继续执行，再补执行计划

## 100% 需求映射要求

- 不允许只写“看起来覆盖了主流程”的大概结论
- 必须把原始需求拆成可检查条目
- 每个需求条目都要有去向：
  - 已生成用例
  - 明确不测
  - 待确认
- 如果还有“未处理”的需求条目，用例设计不能视为完成

## 覆盖建议

每个核心需求至少包含：

- 1 条正向主流程
- 1 条关键逆向或异常流程
- 1 条边界或限制规则

每个状态流转对象至少包含：

- 合法流转
- 非法流转
- 回退或重复操作

每个权限相关需求至少包含：

- 有权限
- 无权限
- 越权入口被拦截或隐藏

同时建议考虑以下质量属性维度：

- 功能性
- 易用性
- 兼容性
- 安全性
- 性能

## 可执行性判定

一条用例只有同时满足以下条件，才可标记 `automation_candidate: high`：

- 页面入口明确
- 元素可被稳定识别
- 步骤不依赖人工判断图像细节
- 断言可客观判定
- 测试数据可重复准备

## 优先级硬要求

优先级是执行资源、回归范围和风险暴露的核心输入，不是可选标签。测试点和最终用例只允许使用以下三级，并必须写明 `priority_rationale`：

| 优先级 | 风险等级 | 判级口径 | 全量用例占比 |
|---|---|---|---:|
| `P0` | 高 | 核心主流程、资金/库存/权限安全、关键交易链路、关键状态流转、不可逆或高影响操作 | 20%~25% |
| `P1` | 中 | 主要业务分支、重要校验、常见异常、可恢复但影响主要功能的错误 | 35%~40% |
| `P2` | 低 | 边缘场景、低频异常、次要边界、展示/易用性、扩展兼容和低影响验证 | 35%~40% |

硬性规则：

1. `05_test_points.yaml` 和 `06_final_test_cases.yaml` 的每一项都必须包含 `priority: P0|P1|P2` 和非空 `priority_rationale`。
2. 同一测试点与最终用例的 `priority`、`priority_rationale` 必须完全一致。
3. 全量用例集必须同时包含 P0、P1、P2，不允许以“本项目都很重要”为由把大部分用例标成 P0。
4. 最终用例数达到 20 条时，按精确百分比校验上述区间；低于 20 条时只允许单条用例造成的整数取整误差，但仍必须包含三档。
5. 判级先依据业务风险，再检查组合占比；禁止为凑比例随机升降级。若风险判级后占比越界，必须回查是否把普通字段校验、低频边界或展示兼容误标为 P0/P1。
6. 任一等级缺失、占比越界、判级理由为空、出现 P3/高/中/低等非标准值，或测试点与最终用例不一致，均视为设计门禁失败。

`priority_rationale` 应说明业务影响，而不是复述等级。例如：

```yaml
priority: "P0"
priority_rationale: "涉及余额扣款和订单状态提交，错误会造成资金与交易数据不一致"
```
