# 用例评审标准

## 人工介入预审（一票否决）

逐条审核 `execution_readiness`：交易/付款/扫码是否标为 manual；复杂前置的人工数据/权限/配置是否列入 assisted 或 manual 的准备事项；每项是否具备负责人、具体内容与验收条件；自动造数声明是否有当前环境的依据。不得将人工核心操作标为 assisted，也不得把人工依赖标为 auto。缺少分级或隐瞒人工依赖，不得给出通过结论。执行前还必须向测试人员展示清单，完成真实确认或人工跳过决定，详见 [human-readiness.md](human-readiness.md)。

## 目标

在执行前用统一口径筛掉无效、模糊、重复和不可执行用例。

评审不仅检查内容质量，还要承担“补全与修正”的职责。
评审前必须重新将用例与需求文档逐条回比，不能只基于上一步产物继续往下走。若使用 `case_normalization` 模式，必须同时回比已有 XLSX 的源行和导入报告，不能只审查 AI 生成后的新文本。

评审分数是人工质量判断，不能替代机器门禁。评审修订完成后必须输出唯一最终源 `06_final_test_cases.yaml`，并与 `05_requirements.yaml`、`05_test_points.yaml` 一起通过 `validate_case_design.py`；门禁未通过时，评分再高也不得进入执行。

## 已有用例规范化评审

使用 `case_normalization` 时，在 11 维评分前增加专项审计：

- 确认原 Excel 文件、工作表、源行、原 ID 和 SHA-256 可追溯；
- 统计原样保留、修订、拆分、合并、新增和拒绝的用例；
- 逐条说明语义变化，禁止只写“已优化”或“已符合规范”；
- 识别原用例中的跨用例依赖、多主断言、不可执行前置和缺失反馈分支；
- 有 PRD 时记录 Excel 与 PRD 的冲突和补充覆盖；
- 无 PRD 时把需求完整性标记为 `not_assessed`，不得用虚构需求或测试点填充数量门槛；
- 专项结论为 `revise_required` 或 `reject` 时，11 维评分不能把它改判为通过。

## 评审维度

每条用例按十一个维度评审：

1. 需求覆盖
2. 业务正确性
3. 步骤清晰度
4. 断言可判定性
5. 数据可执行性
6. 依赖与风险显式化
7. 可自动化程度
8. 无重复冗余
9. 兼容性与质量属性覆盖
10. 排序与需求顺序一致性
11. 字段覆盖完整性（核心表单类功能）

## 评审结论

- `pass`
- `pass_with_minor_comments`
- `revise_required`
- `reject`

## 评审评分规则

每个维度按 0-2 分打分：

- `0`: 明显不满足
- `1`: 基本满足但存在缺口
- `2`: 满足且表达清晰

总分 22 分（十一个维度），建议阈值如下：

- `18-22`: 通过
- `14-17`: 小改后通过
- `9-13`: 必须修订
- `0-8`: 驳回重写

## 优先级专项评审（硬门禁，不计入22分）

优先级不新增第十二个评分维度，避免改变现有11维、22分体系；它作为用例集级专项评审和一票否决项独立执行。评分达到18分但优先级专项失败时，整体评审结论仍必须是 `revise_required` 或 `reject`。

### 单用例判级检查

- `priority` 只允许 `P0`、`P1`、`P2`。
- 每条测试点和最终用例都必须包含非空 `priority_rationale`，说明失败后的业务影响。
- 测试点与其唯一最终用例的 `priority`、`priority_rationale` 必须完全一致。
- P0：核心主流程、资金/库存/权限安全、关键状态流转、不可逆或高影响操作。
- P1：主要分支、重要校验、常见异常、影响主要功能但可恢复的错误。
- P2：低频异常、次要边界、展示/易用性、扩展兼容和低影响验证。
- 不得因“该功能重要”就把该功能下所有字段、边界和兼容用例都标成P0。

### 用例集占比检查

| 等级 | 强制占比 |
|---|---:|
| P0 | 20%~25% |
| P1 | 35%~40% |
| P2 | 35%~40% |

- 20条及以上按精确百分比校验。
- 少于20条只允许一条用例造成的整数取整误差，但P0/P1/P2仍必须全部存在。
- 评审文档必须列出总数、三级数量、三级占比、允许数量区间、越界项和整改后的分布。
- 必须先按风险逐条判级，再核对占比；禁止仅按配额随机调整。
- `07_case_design_gate.json.priority_policy.status` 必须为 `pass`，人工评分不能豁免机器占比门禁。

## 逐项检查清单

### 环境可执行性专项（硬门禁，不计入22分）

- 抽样用例数不得少于总用例的 10%，向上取整；其中 P0 抽样不得少于 P0 总数的 20%，向上取整。
- 每个抽样项必须实际探测可用 UI、API 辅助、数据构造或账号通道，记录 `channels_tried`、证据、`executable/risk/blocked` 状态和非可执行时的修订动作。
- 抽样发现控件语义、前置数据或执行通道错误时，必须先修订用例或 execution profile 再重新评分，不能只留风险后放行。
- 全部用例都为 22/22 时，`perfect_score_justification` 必须引用逐项证据；机械满分且无证据视为评审无效。

### 1. 需求覆盖

- 是否关联了明确需求 ID
- 是否与原始 PRD 条目逐条回比，而不是只参考拆解结果
- 是否覆盖主流程
- 是否覆盖关键分支或限制规则
- 是否存在明显漏测

### 1.1 强制回比规则

- 每条最终用例都必须能回溯到至少一个原始需求条目
- 每条原始需求条目都必须有处理结果：已生成用例、明确不测、待确认
- 必须输出“需求条目 -> 用例ID”的映射关系
- 如果存在未映射需求条目，评审结论最高只能是 `revise_required`
- 如果存在与 PRD 冲突的用例内容，评审结论最高只能是 `revise_required`
- 每个测试点必须且只能映射一条最终用例，测试点与最终用例粒度必须一致

### 2. 业务正确性

- 前置条件是否符合真实业务
- 前置条件是否只引用当前 PRD / 当前项目背景 / 当前环境探测结果；不得把别的项目里的默认资源（如图片库、验证码、统一登录方式）当成当前项目的既有条件。当前项目未明确的支持资源，不应在设计阶段直接判死，而应检查是否已经提供 `data_setup` / setup strategy 作为执行期探测与构造路径
- 步骤顺序是否符合用户实际操作
- 预期结果是否符合 PRD 或通用业务规则
- 正式用例内容是否只来自 PRD、原型/截图、用户背景说明或明确测试设计推导；不得混入历史执行记忆、接口字段、执行脚本变量或页面探索偶发现象

### 3. 步骤清晰度

- 步骤是否原子化
- 是否能被不同执行者一致理解
- 是否避免“适当”“正常”“成功后”等模糊词
- 正式表格中的步骤是否为中文业务操作，且不暴露 `open_url`、`click`、`assert_text`、`execution_profile` 等执行器动作名或内部字段名
- 正向字段用例若声称值已保存，是否明确包含保存/提交、重新查询或打开同一对象、输入值与回显值比较；只输入不保存必须打回

### 4. 断言可判定性

- 是否可观察
- 是否可客观判断
- 是否能明确区分通过与失败
- 预期结果是否自包含写明业务结果、页面反馈、状态变化、金额/字段回显或提示文案；禁止仅写“符合 PRD 约束”“与需求一致”“校验通过”
- `result_contract.observations` 是否能逐项机器求值，且来源、运算符、期望值和证据要求完整
- 拒绝/拦截类是否同时验证拒绝证据和 `mutation_committed=false`，避免“提示出现但数据已写入”的假阳性
- `result_contract.assertion_policy` 是否完整划分每个 observation 的 `hard/soft`；硬断言决定业务结论，软断言只记录表现差异
- 精确 UI 提示文案作为硬断言时是否有 PRD 逐字依据并声明 `prd_exact: true`；无逐字依据必须降为软断言
- 拒绝类 `mutation_committed=false` 是否始终为硬断言；提示出现不能替代副作用验证
- `persisted_validation` 是否包含 `object_id/input_value/persisted_value/persistence_verified/mutation_committed`；`edit` 是否额外包含 `before_value`，且三值会进入执行结果和回填
- 变化类用例（编辑、删除、选择/取消、重新上传、合并、添加、提交、状态流转）是否声明 `change_evidence.required=true`、变化类型和前后断言；每次 attempt 是否规划并保留 before/after 两张独立截图
- 变化结果是否具备 `before_value/after_value`（或前后状态）、`changed`、`comparison_verified`，且前后截图能通过同一对象标识和内容锚点对应；缺任一项不得评审通过

### 5. 数据可执行性

- 测试数据是否给出
- 数据是否可构造
- 数据是否会污染后续执行
- **硬性检查（2026-08-24 新增，一票否决项）**：
  - 前置条件必须属于三态之一（自造 / 系统预置 / 环境提供），禁止写"存在商品/存在订单"这类无来源声明
  - 自造态：前置条件必须写清需要的业务状态/数据来源；构造策略可放在独立 `data_setup`/`setup strategy`，但不得写进正式业务步骤
  - 系统预置/环境提供：必须标注来源 + 带"数据缺失 → blocked"兜底
  - 违反以上任一条 → 本维度 0 分 + 打回补全（详见 case-design.md「前置条件三态」）

### 6. 依赖与风险显式化

- 是否标注环境依赖
- 是否标注账号角色依赖
- 是否标注外部系统依赖
- 是否标注 PRD 歧义风险

### 7. 可自动化程度

- 步骤是否适合浏览器驱动
- 元素是否可定位
- 断言是否可脚本化
- 是否存在无法稳定复现的操作

### 8. 无重复冗余

- 是否存在高度重合用例
- 是否可以合并重复步骤
- 是否存在一条用例覆盖多个独立验证点
- 是否恰好只有一个主断言；多个可独立判定的预期必须拆成多个测试点和多条用例
- 用例名称是否描述测试点，预期结果是否描述执行后的可观察结果；两者高度重复时本维度最高 1 分

### 9. 兼容性与质量属性覆盖

- 是否考虑兼容性
- 是否考虑安全性、性能或可用性
- 是否对关键质量属性有最小覆盖

### 10. 排序与需求顺序一致性

- `case_ordering.policy` 是否为 `prd_port_page_group`，`group_sequence` 是否能追溯到当前 PRD 的首次出现顺序
- 测试点与最终用例是否均有非空且一致的 `feature_group`
- 是否按“PRD 首次出现顺序 → 端口 → 页面/相似功能集合 → 集合内场景顺序”编排
- 同一 `feature_group` 是否形成连续区间，禁止被其他集合穿插
- 同页面或相似功能的场景级、字段级、边界/异常用例是否聚合在一起
- Excel 行顺序和“功能集合”列是否与唯一最终 YAML 完全一致
- 缺少功能集合、集合被拆散、顺序无法追溯或 Excel 与 YAML 不一致时，本维度记 0 分并打回

### 11. 字段覆盖完整性（核心表单类功能）

针对创建/编辑、下单、发货、售后处理、用户信息等核心表单类功能，检查：

- 输入框是否覆盖：有效（中文/英文/数字/特殊字符）、无效（空/空格/超长）、必填（填/不填）、类型专项（价格/手机号/库存）、边界值
- 下拉框是否逐项选择并校验数据
- 上传是否覆盖合法格式 + 非法格式
- 复选框/多选是否覆盖选中、未选中、混选
- 数据统计类是否覆盖数据变动影响 + 点击跳转明细

判定规则：

- 非表单类功能（列表、跳转、展示）不适用本维度，标 `N/A`
- 表单类功能若核心字段缺字段级用例，该用例集标记 `revise_required`，打回补充字段用例
- 字段用例按 case-design.md「字段级覆盖规则」批量补充，不重复评审业务正确性

## 一票否决项

出现以下任一情况，直接 `reject` 或 `revise_required`：

- 无需求来源
- 未完成需求文档逐条回比
- 存在未映射需求条目且未说明原因
- 无明确预期结果
- 步骤缺少关键动作
- 使用大量主观判断词
- 测试数据不可得
- 前置条件无法验证
- 测试点与最终用例的 polarity/interface/expected_outcome 不一致
- execution_profile 不具备用例要求的 capability 或主通道
- 拒绝类用例缺少 `mutation_committed equals false` 结果契约
- `required_produced_keys` 与结构化 observation 键不一致
- 依赖外部条件但未说明
- 正式用例列出现大量英文执行器动作、内部变量或自动化占位符
- 预期结果需要读者另查 PRD 才能判断是否通过
- 用例顺序未按 PRD/业务模块聚合，导致同一模块用例被明显拆散
- 测试点与最终用例不是严格一对一
- 最终用例源未声明 `case_source.artifact_role: final` 和 `mode: full`
- 用例或测试点的优先级不是 P0/P1/P2，或缺少 `priority_rationale`
- 测试点与最终用例的优先级或判级理由不一致
- P0/P1/P2 任一等级缺失，或三级占比不满足 P0 20%~25%、P1 35%~40%、P2 35%~40%（小于20条仅允许整数取整误差）
- `07_case_design_gate.json.priority_policy.status` 不是 `pass`
- 缺少硬/软断言策略、断言键未完整划分，或拒绝类 `mutation_committed` 不是硬断言
- 环境可执行性抽样不足总用例 10% 或 P0 20%，或探测记录缺通道、证据、修订动作
- 全部用例 22/22 但缺少可核查的满分依据
- 正向持久化字段用例缺保存或保存后反查，或编辑用例缺前值、输入值、保存后回显值

## 评审输出格式

每条用例至少输出：

- `case_id`
- `priority`
- `priority_rationale`
- `review_status`
- `score`
- `findings`
- `missing_coverage`
- `revision_actions`

评审汇总还应输出：

- 需求总条目数
- 已映射需求条目数
- 未映射需求条目数
- requirement_to_case_matrix
- 初始产出用例条数
- 需求核对补充条数
- 评审新增或修改条数
- 最终总用例条数
- 用例设计门禁文件与状态（`07_case_design_gate.json: pass`）
- P0/P1/P2 数量、占比、允许区间和 `priority_policy.status`
- 环境可执行性抽样数量、P0 抽样数量、探测通道、证据、风险和修订动作
- 硬/软断言专项结果，以及精确提示文案的 PRD 原文依据
- 22/22 用例数量；全部满分时的逐项满分依据

## 评审动作

评审不只给结论，还必须给修改指令。修改指令要尽量具体，例如：

- 将步骤 3 拆成“点击提交”和“等待成功提示”两个动作
- 将“校验提交成功”改为“校验出现 toast: 提交成功”
- 为该用例补充无权限角色数据
- 增加非法状态下重复提交的逆向用例

评审完成后的最后动作固定为运行用例设计门禁。若门禁失败，根据错误修订需求条目、测试点或最终用例并重跑；禁止手工把门禁状态改为 `pass`。
