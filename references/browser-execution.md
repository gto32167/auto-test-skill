# 浏览器执行与报告方法

## 先提示人工事项，再开始自动化

执行计划必须保留所有用例的 `readiness` 安排。计划门禁自动生成 `10_执行前人工准备清单.md`，Agent 先展示需要人工操作/准备的具体内容、负责人和验收条件；实际人确认后记录清单确认与准备记录。未准备好的用例必须由人明确标记 `skip`，否则整个批次停在执行前检查。`manual` 禁止加入自动执行队列；人工移交与人工跳过分别回填 `not_run/manual_execution_required`、`not_run/human_preflight_skip`，不得当作运行中阻塞或产品失败。所有准备好的自动用例才适用后文的尝试/重试、运行中数据构造和三态判定规则。详见 [human-readiness.md](human-readiness.md)。

回填增加“原因说明（给测试人员）”“建议下一步”“技术原因（给Agent）”：用口语说明失败步骤的预期与实际差异、缺少的条件或人工决定跳过的原因，保留技术明细供 Agent 定位。不得从异常猜测已完成登录、下单或付款。

## 目标

把评审通过的结构化用例转成浏览器可执行任务，并沉淀证据与测试报告。

## 执行源门禁

执行只能读取已通过 `07_case_design_gate.json` 的 `06_final_test_cases.yaml`。执行计划必须通过 `10_execution_plan_gate.json` 后才能启动用例；执行结果必须同时绑定最终用例和执行计划的 SHA-256。

- 禁止读取 `04_scenario_cases.yaml`、初始用例、评审前用例或模板版 XLSX 作为执行源。
- 用例设计门禁失败时，不生成执行计划；执行计划门禁失败时，不开始执行。
- 缺少代码库或接口文档，只跳过代码走查或接口测试，不改变功能用例源，也不降低功能执行范围。

执行计划必须逐条继承用例的语义哈希、`execution_profile`、能力、主通道和意图快照。前置构造写入 `setup_steps`，核心业务动作写入 `core_steps`；两者不得混用。详细结构和命令见 [semantic-contract-gates.md](semantic-contract-gates.md)。

## 执行前准备

执行前必须明确：

- 测试环境 URL
- 账号与角色
- 初始数据
- 浏览器类型
- 是否允许修改真实业务数据
- 截图和日志保存路径

## 环境前置检查门禁（Gate）

正式执行用例前，必须先通过以下环境门禁，全部通过后才允许进入用例执行：

1. **登录态探活**：在首条业务用例开始前加载 `storage_state` → 打开受保护页面探活 → 若跳回登录页则触发自动重采（重新登录后回写 storage_state）→ 后台 / H5 双会话分离管理；较早轮次的 `pass` 不能替代本轮即时探活
2. **权限核对**：确认当前账号可访问的菜单/模块范围；需求范围内的 403 / 无权限模块必须记为 `blocked` 并保留对应结果，只有需求条目已明确标记不测时才可排除
3. **API 通道可达性**：若计划使用 API 兜底，必须从本轮当前项目 `storage_state` 重新构造鉴权头，再探活 API 域（请求一个轻量端点，验证 Code=0）；抓包或探测模板只允许复用请求结构，不允许复用其中保存的 Authorization/token
4. **前置构造通道就绪**：执行计划中声明的数据构造通道（API / UI / 脚本）至少一种真实可用；这表示当前项目有可走的构造路径，不表示所有用例前置都已提前造好
5. **环境声明**：URL / 账号角色 / 是否允许改真实数据 / 数据清理策略，写入执行日志头部

门禁未通过时，记录阻塞原因并停止执行，而不是带着问题往下跑。

若受保护 UI 已可访问、同账号 API 探活也成功，但数据工厂仍集中返回 401/403，优先检查执行器是否仍从旧抓包/探测文件加载 Authorization。确认并刷新当前鉴权后重跑 setup；在此之前不得把所有相关用例笼统回填为“前置数据不可构造”。

## 执行对象筛选

完整交付的计划与结果仍须覆盖 `06_final_test_cases.yaml` 的全部 ID，不允许从结果集中删除 L3、低优先级或人工用例。正式执行顺序是硬规则：`P0 -> P1 -> P2`，同一优先级内保持最终用例原顺序；`level` 和 `automation_candidate` 只决定通道或批次内调度，不得越过优先级顺序。

P0 批次必须完整执行：每条 P0 都先按重试策略 3.0 完成双跑、必要第三遍和最终裁决，不能在首条 P0 失败或某个中间 attempt 失败时提前停止。全部 P0 裁决完成后，只有所有 P0 的最终状态均为 `failed` 才触发 `p0_all_failed_stop_gate`，不启动 P1/P2；只要任意 P0 最终为 `passed` 或 `blocked`，就继续执行 P1/P2。

停止后仍必须保留全部 P1/P2 结果行，统一写为 `status: not_run`、`stability: not_run`、`not_run_reason: p0_all_failed_stop_gate`、`attempts: []`，继续生成执行结果、回填用例、Markdown 和 Word 正式报告。这里的 `not_run` 不是产品通过，也不是环境阻塞，不允许伪造截图、attempt 或业务结论。

以下用例可标记为人工确认或低优先级，但仍须形成 `blocked` / `not_run` / 实际执行结果：

- 依赖 OCR、复杂拖拽、签章视觉比对、验证码
- 依赖第三方不可控回调
- 断言主要依赖人工感知

## 用例到执行任务的映射

对每条用例生成一份执行任务：

- `execution_id`
- `case_id`
- `runtime_env`
- `data_binding`
- `step_mapping`
- `evidence_plan`
- `expected_risks`

执行任务和执行结果的 `case_id` 集合必须与最终用例完全一致，不能只挑 P0/P1 或 L1/L2 交付为“全量执行”。执行计划按 P0/P1/P2 排序；正式结果为便于回填仍保持最终用例原顺序。触发 P0 停止门禁时，未启动的 P1/P2 以标准 `not_run` 占位，合并后的 `11_test_execution_results.yaml` 仍须逐条覆盖最终用例且不得出现额外 ID。

## 浏览器动作约束

执行步骤应尽量使用稳定动作：

- 打开 URL
- 定位元素
- 点击
- 输入
- 选择
- 上传文件
- 等待文本或元素出现
- 校验 URL、文本、状态、列表记录
- 截图

## 稳定选择器规范

选择器是执行稳定性的最大变量，遵循以下规则：

1. **优先语义定位**：`getByRole` / `placeholder` / 可见文本 / 表单 label，而非 CSS 类名
2. **禁止依赖编译混淆类名**：antd / umi / 工程化产物类名可能含反斜杠或哈希（如 `antd-pro\pages\...`），不可作为稳定选择器
3. **中文按钮带空格是常态**：`发 货` `确 定` `确 认` 中间有空格，必须用正则 `发\s*货` / `确\s*认` 或 `filter(hasText)`，不能用精确文本匹配
4. **弹窗确认统一 helper**：封装 `clickConfirm(modal)`，遍历 `/确\s*认|确\s*定|同\s*意/`，避免每种弹窗写死一个按钮名
5. **H5 数字键盘支付**：支付密码可能不是 `<input>`，而是 `.secret-box` + `.keyboard-item` 逐键点击；先点击密码框触发键盘渲染，再逐键点击
6. **显式等待优先**：`waitFor({state:'visible'})` / `waitForURL` / `waitForLoadState`，避免固定 `sleep`

## 页面流转约束（新页面 / 新窗口）

点击某些动作（如“处理退款”“查看详情”）会打开新页面或新 tab：

1. 点击后检查 `context.pages().length`，大于 1 时切换到新页面继续操作
2. 新页面操作完成后关闭，防止页面堆积导致后续定位错乱
3. 若页面跳转导致 URL 变化，以 URL 变化作为流转成功的判定

## 三通道执行模型（默认执行方式）

执行不绑定单一工具。本节是通道职责和切换边界的正式规则来源；`framework-integration.md` 只说明运行副本与框架绑定：

```
通道 A：确定性脚本（主执行）
  builtin_framework / Node+playwright API 脚本
  → 正式用例批量、回归、定时、无人值守
通道 B：Playwright MCP（探索/排障/人工介入）
  会话内逐步驱动，看快照动态决策
  → 首次探索选择器 / 验证码 / 失败现场排障 / 弹窗应变
通道 C：API 直连（兜底验证）
  Bearer + Req-Host 直调业务接口
  → UI 受阻时数据自造 + 业务断言 JSON 佐证
```

### 通道选择规则

- **正式用例默认走通道 A**（确定性脚本），保证可重复、可回归
- **通道 B 用于**：首次执行前探索页面结构确认选择器；验证码/风控现场应变；用例失败后现场排障；人工介入环节（如登录采集）
- **通道 C 用于**：UI 弹窗阻塞 / 时序不稳时的数据构造；金额/库存/状态断言的 JSON 佐证；批量造前置数据
- MCP 探索确认到的稳定选择器与流程，回写 `references/execution-playbook.md` 供脚本通道复用

### 受阻切换流程（L1-L3）

- **L1 通道 A 执行**：验证真实用户路径（默认）
- **L2 切换通道 B（MCP）**：脚本选择器定位失败、弹窗/新页面/验证码等脚本无法应变时，改用 MCP 会话内处理并确认正确选择器
- **L3 切换通道 C（API 兜底）**：UI 被弹窗阻塞、验证码、时序等问题卡住时：
  1. 记录 UI 阻塞现象（截图 + 日志），初判为 UI 缺陷（如弹窗不关闭）
  2. 切换到 API 直连完成数据构造与业务验证（鉴权头 + 关键端点清单见 execution-playbook.md）
  3. 业务功能正确性与 UI 缺陷分别记录，避免 UI 问题连带误判业务功能
- **L4 标记阻塞**：三个通道都不可行时，标记 `blocked` 并写明原因

切换原则：任何一环受阻可切另一通道继续，不中断整轮执行；每轮执行后把新确认的稳定选择器/流程回写经验库。

## 前置构造生命周期（2026-08-24 新增，防止"无数据阻塞"）

**每条用例执行前必须完成前置数据构造，不允许"查不到数据就报阻塞"**。统一生命周期：

```
探测系统形状（只读 API）→ 解析前置条件/选择 setup strategy → 独立构造前置数据 → 执行用例核心 UI → 断言 → 回填 produced
```

1. **前置三态判定**（用例前置条件，见 case-design.md）：
   - 自造态：前置条件写清需要的业务状态/数据来源 → 框架在正式步骤前独立构造
   - 系统预置/环境提供：校验数据存在性，缺失 → 标记 `blocked`（blocker_type=前置缺失），不判失败
2. **造数通道**（按项目选择稳定通道，UI 负责核心行为验证）：
   - 前置数据可由 **API 或 UI** 构造，优先选择当前项目里最稳定、最可复用的通道；构造动作属于执行器，不写入正式业务步骤
   - 造数辅助数据（图片/分类/标签/配送员等）：按当前项目实际支持通道准备；可复用、上传、创建或由环境提供，但不能默认继承其他项目资源，也不把资源准备动作写进正式用例步骤
   - UI 通道只用于"**行为验证**"类用例：列表搜索到商品、编辑页字段回显、页面加载、H5 下单支付链路——**UI 是验证手段，不是造数路径的一部分**
3. **只读形状探测先行（禁止盲猜写参）**：执行前先用 Get 类只读接口摸清系统参数语义——`GetSupportDelivery`（发货方式）、`GetTagList`（标签）、`GetFirstAndSecondList`（分类）、`GetProductListWithPage`（商品/存量图片）。**参数格式未知时禁止盲猜**（如 delivery 盲探对象数组 5 次全 400 的教训），用只读接口或 UI 抓包一次拿权威格式
   - 抓包可保留 URL、方法、内容类型和请求体形状；Authorization、Cookie 和临时 token 必须在本轮执行时从当前项目登录态重新生成，不能固化进数据工厂模板。
4. **字段校验类用例（L3 字段覆盖）用 API 双向判定**：Create/Update 造数后直接改目标字段 → 看接口是否接受 → **该拒的拒了 = passed；该拒的没拒 = failed（真校验缺陷）**；不当失败报"工具未触发"
5. **造数失败处理**：构造通道失败时按原因标记 `blocked`（blocker_type=数据工厂/前置缺失/工具定位）——**仅在无法确认产品缺陷时才阻塞**；UI 交互没走通是"工具定位"不是"数据工厂"
6. **造数结果回填**：工厂返回的 `{id, name, orderNo}` 写入 `runtime/<case_id>_data.json`，并进入用例 produced（订单号/商品名/金额出现在"实际结果"列）
7. **幂等与清理**：造数命名带时间戳/随机后缀；用例结束后 delete 清理（create→update→delete 自产自销），不污染存量

**执行端自检**：用例前置为"自造"但执行脚本无构造逻辑 → 该用例结果不可信，需补独立 setup strategy 后重跑。

**结构化输入数据契约（fixture_contract）**：凡上传 Excel/CSV/JSON 或其他表格文件的用例，必须在进入 UI 上传前执行数据自检。契约至少声明文件格式、必填表头、预期缺失表头、应为空/非空字段和预期反馈类别；执行器必须校验表头与每行列数一致、缺失字段集合准确、目标空值/非空值符合契约。自检失败属于测试数据构造失败，禁止进入产品结果统计。文件被页面拒绝也不等于目标断言通过，必须匹配预期反馈类别和字段锚点；通用“读取内容异常”不能满足“缺少某表头”或“某字段为空”的字段级断言。

### 云商城实测参数语义（示例，换系统用只读探测替代）

- `Product/CreateProduct` body：`delivery` 是**整数数组** `[1,2,3]`（1=快递/2=同城/3=自提），`freight` 是**独立顶层字段**（如 0.01），`picture` 为 `[{imageUrl, width, height}]` 数组，`productType` 1=实物/2=电子卡券/3=虚拟
- `Product/GetProductListWithPage` 返回存量商品（含图片 URL 可复用）；`Order/GetOrderList` 返回 `Data.DataList`（不是 Rows）
- **订单发货链路（2026-08-25 实测，背景文档的 OrderDeliver 是别名会 404）**：
  - 包裹列表：`SecOrder/GetOrderPackageList?orderNo=<订单号>` → `Data.PackageList[].Id` = **packId**（发货后包裹记录保留，可直接反查）
  - 发货：`SecOrder/SendPackage` POST `{packId, IsSecOrder:false}` → `Code=0 发货成功`（**packId ≠ 订单 ID**，来自包裹表；待发货订单 TotalPackageCount=0 需先打包，打包端点未精化）
  - **后端报错会泄露参数名**（`{"Code":30002,"Msg":"参数非法","Data":"orderNo"}` → 直接告诉你该传 orderNo）——参数不明时故意传错 1 次拿报错信息是高效探测法
- **headless 弹窗操作（发货/退款/收货）不可靠**：force click 可能假点击不触发 React 事件 → 误判"点了状态没变"（曾误报 BUG-002，人工在真实浏览器点一次 Code=0 发货成功排除）——**自动化失败 ≠ 产品缺陷，弹窗类操作需人工定性或换 API**

## 失败重试与断点续跑

- 单动作超时（建议 15s）可重试 2 次，重试前先检查页面是否处于可操作状态
- 用例级失败记录 `resumable` 状态；结果文件为追加式写入（每条用例跑完即落盘），中断后可续跑
- 幂等：重跑同一用例不产生重复数据（测试数据带唯一标识）
- 长流程执行（多阶段用例）分阶段落盘中间产物，便于定位失败阶段
- 业务状态等待必须先刷新，再按 0.5s 起步的指数退避轮询到显式超时上限，并把状态时间线写入 attempt；禁止用固定 sleep 后读一次页面作为最终断言
- 预期 UI 提示的用例必须按 `execution-playbook.md` 的“瞬态提示捕获”执行：动作前快照，动作后以短间隔有界轮询 modal/toast/inline/banner，提示可见时立即读取并截图；固定等待后单次读页面不构成有效证据
- UI 字段执行前按 label、name、input type、editable 和最近容器完成控件语义审计，避免把只读展示值或相邻字段当作目标控件
- 判 `blocked` 前按计划执行 UI、API 辅助观察、数据构造等能力探测，结果写入 `capability_probe.attempted_channels` 和 `probe_log`

## 用例级重试判定规则（重试策略 3.0）

重试必须调用 `references/scripts/execution_quality.py` 或等价的 `assets/templates/retry-framework.js`，禁止各执行脚本自行解释。执行模式先由计划门禁固定：

1. `qualification` 用于首次完整交付、输入变化或无可信基线，所有 P0/P1/P2 至少执行两遍。
2. `risk_based_regression` 用于有门禁基线的回归。P0/P1 至少双跑；P2 仅在当前/基线输入 SHA-256 一致、历史至少 2/2 稳定通过、需求未受影响且基线结果有 SHA-256 时允许单跑。
3. 首两遍只有 `passed-passed` 可作为稳定通过。其他任意组合必须补第三遍，禁止“一过一败”或“一过一阻塞”在两遍后收口。
4. 非 P0 以第三遍完整语义证据裁决，状态为 `unstable`；第三遍仍无法判定时为 `blocked`。
5. P0 补第三遍后必须至少 2/3 通过才能 `passed`，至少 2/3 失败才能 `failed`，其余为 `blocked`。
6. P2 单跑失败或阻塞必须立即升级到三遍完整路径，`full_retry_upgraded: true`。
7. 早期一次阻塞可在后续恢复，但恢复遍仍必须完成核心动作、语义契约和证据；不能只把状态字段改成通过。
8. 每次尝试全部保留 attempt、语义哈希、轨迹、observations、produced_data 和证据。最终结果必须与 `selected_attempt` 同值。
9. 正常执行器在首两遍双通过后停止；如果审计结果仍记录了第三遍，该遍证据不得被忽略。非 P0 按第三遍裁决，P0 仍按 2/3 严格多数，并把矛盾结果标为 `unstable`。

重试裁决与优先级停止的先后关系固定为：`完成单条 P0 最终裁决 -> 继续下一条 P0 -> 全部 P0 完成 -> 评估停止门禁 -> 决定是否启动 P1/P2`。attempt 中间态不得直接触发停止。

### 三态判定（passed / failed / blocked，2026-08-24 新增）

最终状态必须是三态之一，**禁止只用两态**：

| 状态 | 定义 | 判定条件 |
|------|------|----------|
| `passed` | 通过 | 有可靠证据证明产品行为符合预期 |
| `failed` | 失败（真缺陷） | **有可靠证据**证明产品行为不符合预期（如截图显示动作已发生但状态未流转、金额公式错误） |
| `blocked` | 阻塞（无法判定） | 环境/工具/前置条件不满足或证据不足，**无法确认是否产品缺陷**（如 UI 弹窗自动化无法触发、登录页定位失败、断言口径待产品确认）；**不判产品失败**，保留观察 |

- **blocked 必须带分类归因**：`blocker_type`（环境/工具/前置/证据不足/口径待确认）+ `blocker_reason`（具体原因）
- **failed vs blocked 的核心区别**：是否有"可靠证据证明产品行为不符合预期"。有证据→failed；证据不足/工具无法确认→blocked
- **通过率双口径**（报告必须两个都写，禁止只给一个）：
  - 含阻塞通过率 = passed / 总数（阻塞计入分母）
  - 已判定项通过率 = passed / (passed + failed)（阻塞不计入）
- 阻塞项不参与"缺陷清单"，但必须在报告中列出并标注"待人工复核"；人工复核确认是真缺陷后升级为 failed 并登记缺陷

判定规则速查表：

| 尝试序列 | 最终判定 | 回填来源 |
|----------|----------|----------|
| 成-成 | passed | 取第 1 遍结果（两遍一致） |
| 成-败-成 | passed + unstable | 取第 3 遍 |
| 败-成-败 | failed + unstable | 取第 3 遍 |
| 阻-成-成（非 P0） | passed + unstable | 取第 3 遍，证明能力已恢复 |
| 败-败-成 | passed + unstable | 取第 3 遍（补跑通过） |
| 败-败-败（有证据不符预期） | failed + unstable | 取第 3 遍 |
| 败-败-败（证据不足/工具问题） | **blocked** | 取第 3 遍，附 blocker_type/reason |

> P0 对上表再应用“至少两遍通过/失败”的多数规则；一次偶然成功不能作为 P0 放行依据。

## 输入一致性校验（SHA-256，2026-08-24 新增）

执行前对输入文件（PRD 原文、环境信息、项目背景等）计算 SHA-256，写入结果 meta 的 `input_sha256`；执行/复核时校验与基线是否一致：

- 输入哈希一致 → `input_identity_verified: true`，基线结果可复用/可对比
- 输入漂移（哈希变化）→ 必须重新拆解/执行，禁止复用旧基线结果
- 报告「基本信息」标注输入一致性状态，防"换了 PRD 还拿旧结果充数"

## 专项复核（recheck，2026-08-24 新增）

本轮执行结束后，对**已实际执行的存疑用例**做一轮独立复核，防"执行通过但实际有问题"漏检。P0 停止门禁导致的 P1/P2 `not_run` 没有执行事实，不得生成伪复核：

- **复核对象**：原 failed / blocked 全部 + 高风险 passed 抽查（如金额/库存/状态流转类按 ≥20% 抽样）
- **复核方式**：独立脚本重跑一遍，或用 API/页面快照做业务状态佐证；复核结果记入用例 `recheck` 字段（passed→confirmed / 反转→注明）
- 复核发现 passed 用例实际有问题 → 降级为 failed/blocked 并登记缺陷
- 复核记录保留在结果 yaml（`recheck` 字段），报告单独一节「专项复核结果」

## 基线复用披露（防"复用洗白"）

若执行结果复用了历史基线（同一输入、环境未变），必须显式披露：

- 每条复用用例标注 `baseline_backfilled_round`（来源轮次），禁止无标注复用
- 结果 meta 披露**复用占比**（如「92/102 来自基线，占比 90.2%」）
- 复用基线的关键用例（高风险/金额/状态流转）必须独立复核至少 1 次，不能全部照抄
- 目的：任何"通过"都必须可追溯到真实执行或已披露的基线，防止拿旧数据充数误导决策

## 用例集指纹

对最终用例表（06 表 / 08 xlsx）计算内容哈希作为 `case_set_fingerprint`，写入结果与报告：

- 回填版/报告引用用例时校验指纹一致，防跨项目编号错位、用例定义漂移
- Codex 项目曾出现报告引用 TC-SP-099 定义与源表不一致（编号错位）——指纹可拦截此类问题

**回填内容硬性要求（不是状态标记）**：

- 回填到用例文件的「实际结果」列必须是该遍执行**产生的业务数据**，供人工复审：创建/编辑的商品名与 goodsId、生成的订单号、订单状态、金额/运费/库存数值、拦截提示文案、页面可见性等
- **必须包含可定位的操作对象（"可找得到"原则）**：
  - 修改/编辑类用例（改商品/改订单/改分类等）：必须回填操作对象标识——`商品名 + goodsId`（如「修改 AI商品_78264729 (goodsId=27323) 价格→16.6」），禁止只回填「XX可编辑: true」
  - 查询类：回填查询条件 + 结果（订单号/商品名/条数）
  - 创建类：回填创建出的名称 + ID（goodsId/分类ID/标签ID）
  - 校验/拦截类：回填触发校验的字段 + 系统提示文案
  - 订单/支付类：回填订单号 + 状态 + 金额
  - 判定标准：复审者仅凭「实际结果」列就能定位到具体数据对象（去系统里搜到它），否则回填不达标
- 每个 `runOnce` 必须返回 `produced` 对象（结构化业务字段，含操作对象标识），禁止只返回 `detail: 'passed'` 之类的状态字符串
- 每条最终用例必须在 `result_contract.observations` 声明通过条件，并保证 `required_produced_keys` 与观察键完全一致；字段存在但值不满足比较规则仍然失败
- 落盘时必须保留完整 `attempts`（attempt / status / semantic_contract_sha256 / execution_trace / observations / produced_data / detail），禁止用 `map()` 丢弃语义轨迹和证据只留状态（详见 execution-playbook.md「回填数据沉淀」）
- 回填必须使用 `references/scripts/backfill_case_execution_results.py`，并同时提供已通过的用例设计门禁和执行结果门禁；脚本从保留 attempts/produced 的 `11_test_execution_results.yaml` 读取，把业务数据格式化为可读中文（如「订单号=2608xxxx，状态=待发货，金额=16.61」）写入实际结果列，状态列单独保留 passed/failed
- 每条结果必须提供结构化 `result_summary`（预期、实际、关键消息、写入结果、业务对象）；`actual_result` 保持 500 字以内，原始 DOM、长响应和全量页面文本只能放日志
- 以 UI 提示作为观察值时，每个 attempt 和最终选中结果还要保留 `feedback_observation`：提示形式、原文、出现耗时、是否自动消失和截图引用。回填使用这些事实说明“何时、以何种形式出现了什么提示”，不能笼统写成“弹框提示”或“UI 断言已满足”

### 人工可读回填格式（2026-09-03 强化）

回填版是交付给产品、研发和测试复审人员直接阅读的文件，不能要求读者解析 YAML、选择器日志或执行器内部状态。每一条用例必须在回填中明确回答以下问题：

1. **前置条件**：账号、测试数据和必要配置是否已准备；不得只写“执行器自造”，应说明准备的文件/商品/订单/活动/权限类型。
2. **执行步骤**：按实际执行顺序写明已完成的动作；若中途停止，必须指出停在第几步。
3. **预期结果**：沿用评审通过的业务预期，不得改写成机器断言名。
4. **实际执行结果**：只写页面或业务对象的可观察事实（订单号、商品名、数量、金额、状态、提示文案、列表是否为空等），禁止直接粘贴完整 DOM、JSON、Locator 调用栈、URL 或 `UI 断言已采集` 等纯状态词。
5. **失败原因**：说明哪一步的预期没有满足、实际看到了什么，以及是否需要修复后回归；不能只写“断言失败”。
6. **阻塞原因**：说明阻塞阶段、已完成动作、未完成动作、具体原因、当前是否能够判定产品缺陷，以及解除阻塞所需的数据/权限/工具修复；不能只写“前置缺失”或一条执行器异常。

回填展示字段固定包含：`前置条件`、`执行步骤`、`预期结果`、`执行状态`、`实际执行结果`、`失败原因`、`失败步骤`、`阻塞/未执行原因`、`产出数据`、`证据`。状态字段保留机器枚举（passed/failed/blocked/not_run），但人工结论必须写在实际结果和原因字段中。Markdown 使用“一条用例一个审阅卡片”；Excel 保留结构化列，二者内容必须一致。

阻塞项的推荐表述为：“未执行到核心断言。执行停在‘某阶段’；已完成……，未完成……，因此不能据此判定产品功能失败。解除条件：……。”技术定位问题（如文件控件未挂载、radio 被误当输入框）与业务前置缺失（如限购商品、活动、异步订单状态未准备）必须分开统计。
- 最终失败项必须包含缺陷严重级别建议、确认状态、责任人、缺陷状态和回归状态；AI 疑似不得在未确认时伪装为已确认缺陷

## UI 截图留证（硬性要求，2026-08-24 新增）

**每条执行的 UI 用例必须保留关键证据截图，以用例编号命名，截图内容对准关键断言时刻**。纯 API 用例不伪造页面截图，其 observations 通过独立请求/响应或日志 `evidence_refs` 留证：

- **命名**：`TC-SP-002.png`（严格用用例编号，不用描述性名称；失败用例可附加 `TC-SP-002_fail.png` 失败现场）
- **存放**：项目 `artifacts/screenshots/` 目录
- **拍摄时机（截图必须"刚好截出"关键信息）**：
  - 校验/拦截类用例（如名称空、价格负数、库存空）：**截图必须包含系统弹出的提示文案**（toast / 表单内联错误 / 弹窗），截出提示即证明校验生效
  - 创建/编辑类：截图包含保存成功后的列表行（可见商品名/价格/库存）
  - 订单/支付类：截图包含订单状态页（订单号 + 状态 + 金额）
  - 失败用例：截图包含失败现场（弹窗未关 / 按钮未响应 / 状态未流转）
- **实现**：批次脚本内置 `shot(page, caseId, tag)` 帮助函数（`page.screenshot({path: SHOTS/caseId.png})`），在断言点前后各截一张；框架在用例结束时检查截图文件存在，缺失则记录 `evidence_missing`
- **回填联动**：回填版 xlsx 增加「截图」列（填 `TC-SP-002.png` 或 `-`），便于复审时对照图片
- **证据 manifest**：每个截图记录真实文件 SHA-256、case_id、断言时刻、目标、浏览器、UI 语义键、`content_text`、必须出现在文本中的 `content_anchors`、验证方法和 `content_verified: true`。API 观察通过自己的 `evidence_refs` 绑定，不伪装成截图内容。
- **兼容性**：每个要求浏览器提供独立截图或独立 `video_frame + frame_id`，禁止多个浏览器共用同一证据身份。

### 变化类操作的前后对比证据（2026-09-02）

凡是用例会让页面、业务对象或订单状态发生可见变化，必须在同一次 attempt 中保留“变化前”和“变化后”两张独立截图，并在结果中声明对比结论。至少包括：

- 编辑/修改：修改商品、数量、地址、规格、留言、订单信息等；
- 删除/移除：删除商品行、异常行、收藏/清单记录、失败记录等；
- 选择/勾选/取消选择、重新上传、合并、添加商品等会改变列表或统计的操作；
- 提交、状态流转、导入落库、结算和异步结果等会改变业务状态的操作。

用例在最终 YAML 中声明：

```yaml
change_evidence:
  required: true
  change_type: edit           # edit / delete / change / state_transition
  comparison_required: true
  before_assertion: 操作前对象、字段或列表状态
  after_assertion: 操作后对象、字段或列表状态
```

执行计划的 `evidence_plan` 必须包含 `before_after: true`，并为每个 attempt 规划独立文件：
`<case_id>_A1_before.png`、`<case_id>_A1_after.png`；第三次执行相应使用 `A3`。最终 canonical `<case_id>.png` 仍从选中 attempt 的 `after` 截图复制，同时 manifest 必须登记 before/after 两个文件、各自 SHA-256、断言时刻和内容锚点。

截图要求：

1. before 必须在执行变化动作前、完成前置数据加载后拍摄，并能定位同一业务对象（名称、编号、订单号或商品 ID）；
2. after 必须在动作完成、状态稳定或重新查询/打开对象后拍摄，必须显示变化后的字段/列表/状态；
3. 结果 `change_comparison` 至少包含 `before_value`、`after_value`（或 `before_state`、`after_state`）、`changed: true/false` 和 `comparison_verified: true`；
4. before/after 任一截图缺失、对象无法对应、或两张图实际内容无法证明差异时，结果最多为 `blocked`，不得仅凭操作成功或接口返回判定通过；
5. 编辑和删除类用例禁止只截编辑页空白视口或删除后的列表；必须同时保留操作前现场，删除后还要说明对象不可见/数量减少等可审计差异。
6. manifest 的 `phase: before` 与 `phase: after` 必须分别引用对应的 `before_state`/前值和 `after_state`/后值文本；`content_anchors` 至少包含截图中实际可核对的业务值、字段标签或状态文案，禁止把同一条 after 摘要复制到 before manifest。

### 证据时刻、字段定位与尝试绑定（2026-09-01）

- 截图必须在最终断言已经完成之后拍摄，不能只在进入页面或打开编辑页时统一截取当前视口。
- 字段创建/编辑类必须先把断言字段或其所属表单项滚动到视口，再截图；截图至少包含字段标签、字段当前值和可定位的业务对象（名称、编号或商品 ID）。仅整页 DOM 能读取到字段、但截图视口看不到字段时，证据不合格。
- 创建/编辑类保存后必须重新查询列表或重新打开同一对象，读取并记录保存前值、输入后值、保存后回显值（适用时）以及对象 ID。只记录接口成功或“编辑页已打开”不能判定通过。
- 每次 attempt 使用独立文件名（例如 `TC-041_A1_after_reopen.png`）；最终结果的 manifest 必须声明 `selected_attempt` 对应文件或由该文件生成的 canonical 副本，禁止后一次 attempt 覆盖前一次截图。
- 最终 canonical 截图必须从 `selected_attempt` 的来源截图复制，二者 SHA-256 必须一致；只填写 `source_attempt_file` 而文件内容不同仍不合格。
- 字段校验、编辑和持久化校验使用 `evidence_scope: assertion_target_container`；订单状态、列表结果等场景用例使用 `assertion_state_view`。诊断占位图不能作为通过证据。
- manifest 的 `content_anchors` 必须包含实际断言值或字段标签，不能使用“店铺”等通用导航词；`observed_target_text` 必须来自截图目标容器或滚动后的断言状态视图并实际命中全部锚点，`content_text` 只是供复核的结果摘要，不能替代实测文本。
- 交付门禁至少校验：文件存在和哈希、case/attempt 及 selected source 绑定、浏览器模式、证据范围、字段语义键覆盖、实测文本锚点和目标可见性。缺少目标字段截图时，结果最多为证据不足的 `blocked`，不得作为正式 `passed`。

## 执行结果与交付门禁

执行结束后必须先运行 `validate_execution_delivery.py --phase execution`，并传入 `--execution-plan-gate` 与 `--execution-plan`。门禁检查最终用例、执行计划和结果版本一致，逐 attempt 轨迹一致，重试 3.0/P0/P2 单跑资格、硬软断言、结构化结果、blocked 能力探测、截图文件/哈希/语义清单、范围矩阵、资源预算、缺陷生命周期和汇总指标全部闭合；失败时禁止生成回填版与正式报告。

回填只能通过 `backfill_case_execution_results.py` 从已通过门禁的 `06_final_test_cases.yaml` 和 `11_test_execution_results.yaml` 生成。随后运行 `validate_execution_delivery.py --phase delivery`，检查模板版/回填版行数、ID、状态、实际结果、OpenXML 结构，并在 Windows 上用已安装的 Excel/WPS 实际打开读取。交付门禁失败时不得声明交付完成。

完整命令、标准文件名和停止条件见 [delivery-gates.md](delivery-gates.md)。

## 证据三通道

每条执行用例必须按实际通道保留完整证据，不要求每条机械凑齐三种形式：

1. **UI 截图**：UI 用例的关键断言时刻和失败现场（**必须**，以用例编号命名并带 manifest）
2. **API 返回**：API 用例或 API 来源 observation 的请求/响应、Code 和关键字段 JSON（通过 `evidence_refs` 绑定）
3. **日志片段**：失败/阻塞时的调用栈、选择器日志、能力探测和页面文本摘要

## 证据要求

每条执行用例至少保留：

- 执行开始时间与结束时间
- 最终状态
- 与 observation 来源匹配的证据引用
- UI 用例的关键断言截图；API 用例的请求/响应或日志证据
- 关键页面文本或日志摘要

如果执行失败，还需补充：

- 失败步骤号
- 实际结果
- 初步归因
- 是否可重试

## 缺陷判定建议

当以下情况发生时，可初步判定为缺陷：

- 与 PRD 明确规则不一致
- 页面反馈与实际结果不一致
- 状态流转错误
- 越权成功
- 核心字段丢失或错误回显
- 失败后无提示且数据状态不明确

当以下情况发生时，先标记为阻塞或待确认：

- PRD 本身歧义
- 环境异常
- 测试数据不满足前置条件
- 第三方依赖不可用

## 报告结构

正式测试报告必须包含：

1. 测试背景
2. 范围与不在范围
3. 环境与数据
4. 执行概况
5. 缺陷汇总
6. 未执行项
7. 风险与建议
8. 结论
9. **实现与 PRD 差异登记表**（DIFF-ID | 位置 | PRD 预期 | 实测 | 影响面 | 待确认方）—— 实测发现的规则口径差异（如运费、退款金额）不是 bug 但必须暴露给产品确认
10. **执行稳定性与资源指标**：执行率 / 双口径通过率 / 首跑通过率 / 第三遍数 / 不稳定数 / P2 单跑与升级数 / 预计和实际 attempts/分钟 / 环境中断次数 / 登录态重采次数
11. **缺陷生命周期**：确认状态 / 责任人 / 缺陷状态 / 回归状态

正式交付必须同时生成 `23_正式测试报告.docx` 和机器可审计的 `23_正式测试报告.md`。报告不重复逐用例摘要，执行状态、实际结果、产出数据和证据索引以 `18_测试用例_执行回填版.xlsx` 为准。

## 执行结论规则

- 所有 P0 冒烟通过，且无阻塞级缺陷，可给出“可继续测试/可灰度”的正向结论
- 存在阻塞主流程缺陷，不建议上线
- 未执行比例高于 30% 时，不给出完全通过结论
- PRD 歧义较多时，结论需附带假设条件
- 存在“实现与 PRD 差异”但功能行为稳定时，结论需标注“功能通过，口径差异待产品确认”，不得直接判定为失败

## 对浏览器工具的要求

如果有浏览器自动化工具，优先使用：

- 明确等待条件而不是固定 sleep
- 失败时自动截图
- 每步输出简要日志
- 将截图和日志路径写回执行结果

如果浏览器工具不可用，仍需输出：

- 待执行计划
- 阻塞原因
- 预计证据采集方式
