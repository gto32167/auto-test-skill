# AI QA PRD Workflow

Use this skill when the user wants any PRD-driven QA deliverable or wants existing XLSX test cases converted into the workflow's standard gated format: requirement decomposition, existing-case normalization, test case generation, case review, browser execution, backfill, or test report output. The workflow can stop after the requested stage.

## Outcome

Produce artifacts that are directly reusable by another AI agent or test engineer:

- A structured PRD decomposition
- A traceable existing-case import and normalization audit when XLSX cases are supplied
- Executable-style test cases with explicit preconditions, data, and browser actions
- A review result with pass/fail findings against a fixed checklist
- A test case review scoring document (11-dimension per-case scores + dimension summary, see assets/templates/test-case-review.md)
- A non-empty template-based testcase XLSX; use the user's template when provided, otherwise use the workflow's default seven-column template with a `功能集合` column before `用例名称`
- A browser execution plan
- A testcase backfill file that includes execution result and produced runtime data
- A formal Word test report with pass/fail/blocked, stability, scope, resource, defect-lifecycle, and release-gate conclusions

## Working Principles

- Default to `full` delivery unless the user explicitly requests a narrower stage such as generation-only, review-only, execution-only, smoke-only, or rapid regression. Full delivery means L2 scenario coverage plus all required L3 field/boundary/negative coverage; an initial scenario set is never a valid final-case or execution source.
- When the primary input is an existing testcase XLSX, select `case_normalization` instead of treating the workbook as an execution source. Run `references/scripts/import_existing_cases.py`, preserve source workbook SHA-256/sheet/row/ID/column values, audit and normalize the imported cases, then produce the same `05_requirements.yaml` -> `05_test_points.yaml` -> `06_final_test_cases.yaml` -> `07_case_design_gate.json` -> `08_测试用例_模板版.xlsx` chain. Read `references/existing-case-normalization.md` before changing case semantics.
- After executing normalized cases, aggregate child results back to the original XLSX rows with `references/scripts/aggregate_original_case_results.py` and `references/scripts/generate_original_case_result_xlsx.mjs`. A parent original case passes only when every mapped child case passes; any child failure makes the parent failed, while blocked or incomplete child evidence makes the parent blocked. Preserve child IDs, failed steps, reasons, produced data, and evidence references in the parent result copy.
- An import report with `status: pass` proves only that the workbook was read. Existing XLSX rows can enter execution only after normalization and a passed case-design gate; never execute or report counts directly from the workbook.
- If a PRD accompanies existing cases, use the PRD as business truth and the workbook as reusable test assets, recording conflicts and adding missing coverage. Without a PRD, treat the workbook only as a test baseline, set requirement completeness to not assessed, and never claim complete requirement coverage or invent product rules to satisfy a gate.
- Use one canonical artifact chain: `05_requirements.yaml` -> `05_test_points.yaml` -> `06_final_test_cases.yaml`. The final source must declare `case_source.artifact_role: final` and `case_source.mode: full`; keep scenario drafts under an `initial`/`scenario` filename so they cannot be confused with the execution source.
- Treat delivery gates as hard stops, not review advice. Run `references/scripts/validate_case_design.py` before generating XLSX or execution tasks, run `validate_execution_plan.py` after the execution plan and before any case, run `validate_execution_delivery.py --phase execution` before backfill, and run it again with `--phase delivery` before reporting completion. Never continue past a failed gate or silently downgrade a full delivery. When the user only wants generation/review, stop after the template XLSX and review artifacts are produced.
- Prefer structured outputs over prose summaries.
- Treat ambiguous PRD text as a risk and surface it explicitly.
- Write cases so an AI can execute them with minimal interpretation.
- Separate business assertions from UI interaction details.
- Require reviewable evidence for every executed case. Each attempt keeps an independent assertion screenshot; the canonical case screenshot must be byte-identical to the selected attempt source. Field and persistence cases capture the visible assertion field container; scenario cases capture the visible assertion-state view. Manifest v2 binds file SHA-256, case/attempt, configured headed/headless mode, target, semantic keys, anchors, and actual target text. API observations remain bound through their own `evidence_refs`; compatibility cases require separate evidence per browser.
- Every test point and final case must carry a machine-checkable semantic contract. Bind polarity/interface/expected outcome to an executor profile capability, hash that contract into the gated plan, and require every executed attempt to return a matching execution trace and structured observations. Derive `passed` only when all hard result-contract observations match; derive `failed` only when the observation structure/evidence is complete and at least one hard contract observation does not match. Soft mismatches are recorded without changing the business verdict. Missing or inconclusive observations are `blocked`, not product failures. Action/API success must never set status directly.
- When a testcase produces business data during execution, record it back into the testcase result. Examples: order number, created goods name, edited field before/after values, refund amount. Rejected/validation cases must additionally prove `mutation_committed: false`; a prompt alone is insufficient.
- A positive field case that claims a saved business value must use `operation_type: persisted_validation`: enter the value, save/submit, re-query or reopen the same object, and compare the input with the persisted echo. Its result contract requires `object_id`, `input_value`, `persisted_value`, `persistence_verified`, and `mutation_committed`; edit cases additionally require `before_value`. Reading the current input control without committing is not persistence verification.
- The backfill "actual result" column must contain the produced business data (goods name / order no / amount / stock / prompt text), never a bare status string like "passed". For modify/edit cases it must include the target object id (e.g. `goodsId` + goods name) so a reviewer can locate exactly which record was changed; "editable: true" without the object is not a valid backfill. See references/browser-execution.md "回填内容硬性要求".
- Human-readable backfill is mandatory: every row/card must include preconditions, executed steps, expected result, observed business facts, and a separate failure or blocker explanation. Do not expose raw DOM, JSON, selector stack traces, or executor phrases such as `UI assertion not met` as the only explanation. A blocker must state the stopping stage, completed and uncompleted actions, why the product cannot yet be judged, and what data/configuration/tool fix is required before rerun.
- Treat test-case independence as a hard rule: every case must be able to construct its own prerequisite data; referencing another case's execution result as a precondition is forbidden and rejected at review time.
- Treat executable test fixtures as a hard contract, not an implementation detail: for file/table/structured-input cases declare the expected format, exact headers, missing headers, empty/non-empty fields, row/column shape, and expected feedback category. Build rows by field name or from the current product template, validate the fixture before upload, and abort as a test-data construction error when the shape does not match. A malformed fixture must never be reported as a product validation pass.
- Use retry policy 3.0. In `qualification` mode every case runs twice; only two passing attempts are stable. If the first two are not both passed, a third adjudication attempt is mandatory and the result is `unstable` unless the third attempt remains blocked. P0 can pass after a third attempt only with at least two passes out of three. In `risk_based_regression`, P0/P1 still run twice; P2 may run once only when the plan gate proves identical current/baseline input hashes, at least 2/2 historical stable passes, no affected requirement, and a hashed baseline result. An exempt P2 failure or block upgrades immediately to the full three-attempt path. Never end a mixed pair after two attempts and never let an early blocked attempt permanently hide a later evidenced recovery. See references/browser-execution.md and references/delivery-gates.md.
- Execute the gated plan in stable priority batches: all P0 first, then P1, then P2, preserving canonical order within each priority. Finish every P0 case's retry-policy 3.0 adjudication before evaluating the batch. Stop before P1/P2 only when every P0 has a final `failed` verdict. If any P0 is finally `passed` or `blocked`, continue with P1/P2. Keep every unstarted lower-priority case in the result and backfill as `not_run` with reason code `p0_all_failed_stop_gate`, no attempts, evidence, or fabricated business conclusion, then continue through execution gate, backfill, delivery gate, Markdown, and formal Word report. Never stop on an intermediate attempt, after only the first failed P0, or when the completed P0 batch contains mixed final statuses.
- Use a three-state verdict (passed / failed / blocked) for every case: `failed` requires reliable evidence the product behaves against expectation; `blocked` (environment/tooling/precondition gaps or insufficient evidence) must NOT be reported as a product failure and must carry blocker_type + blocker_reason. Always report both pass rates: with-blocked and judged-only (passed/(passed+failed)). See references/browser-execution.md "三态判定".
- Verify input identity before executing or reusing baselines: hash the PRD/environment inputs (SHA-256) into the result meta; reuse of historical baselines must disclose the backfill round and the reuse ratio, and key cases must be independently rechecked. After execution, run a recheck pass over executed failed/blocked cases plus a sample of executed high-risk passed cases, and record it in a `recheck` field. Cases left `not_run` by the P0 stop gate are not rechecked because they were never started. See references/browser-execution.md "输入一致性校验 / 专项复核 / 基线复用披露 / 用例集指纹".
- Classify every result-contract observation as `hard` or `soft`. Hard mismatches decide the verdict; soft message wording may record a warning but cannot hide a satisfied business invariant. Exact UI prompt text may be hard only when the case declares `prd_exact: true`. A rejected mutation must always keep `mutation_committed: false` as a hard assertion.
- For negative cases, distinguish the rejection branch being tested (for example missing header, empty required value, file parse/format, size limit, or business rule). “Any error/异常 toast” is not an acceptable pass assertion. The observed message must match the case's declared feedback category and field anchors; otherwise record a reliable failure or evidence gap with the actual branch.
- During case review, probe environment executability for at least 10% of all cases and 20% of P0 cases, recording channels, evidence, and revision action. A 22/22 score for every case requires explicit full-score evidence. Review scores, priority distribution, environment sampling, and machine gates are independent requirements.
- Before execution, budget attempts and minutes, plan UI/API evidence separately, define capability probes before `blocked`, use refresh plus bounded exponential polling for state transitions, and audit the real label/name/type/editability/container of UI fields. Execution results must use a concise structured `result_summary`; raw DOM belongs in logs. Failed results must carry a severity suggestion, confirmation status, owner, defect status, and regression status.
- Every test case must declare its precondition as one of three states (self-built / system-preinstalled / environment-provided). Self-built is the preferred state and the precondition row must clearly describe the required business state, while any construction details belong to a separate setup strategy / `data_setup` section and must not be embedded in the formal business steps. Self-built cases may use a unified data-construction layer (API or UI, depending on project constraints) and follow the setup lifecycle defined in references/browser-execution.md. Missing data is reported as `blocked` (blocker_type=数据工厂失败 or 前置缺失), never as a bare "no data" abort.
- Preconditions must be sourced from the current PRD, current project background, or current environment probe; do not inherit image libraries, captcha behavior, login methods, or other setup assumptions from previous projects. If the current project does not explicitly describe a supporting resource, keep the formal case focused on the required business state and let execution-time `data_setup` / setup strategy probe and construct it first; only after that path actually fails should the case be marked `blocked`. The formal case should describe the capability needed to execute the step, not a remembered project-specific fixture.
- Layer test cases by coverage granularity: scenario-level cases (L2, main flows, used for smoke/regression) plus field-level cases (L3, every input shape per field, used for full validation). Core form-like functions must follow the field-coverage rules in case-design.md.
- Treat review order as a gated design property. Every test point and final case must declare the same non-empty `feature_group`; the final source must declare `case_ordering.policy: prd_port_page_group` and its ordered `group_sequence`. Arrange groups by their first appearance in the current PRD, then by port and page/similar-function collection; keep every group contiguous and place its scenario, field, boundary, and negative cases together. The generated XLSX must preserve the final YAML order. Read references/case-design.md for the detailed ordering rules.
- Treat testcase priority as a gated portfolio rule, not a free-form label. Use only `P0/P1/P2`, map them to high/medium/low business risk, and require every test point and final case to carry the same `priority` plus a non-empty `priority_rationale`. In full delivery the final-case distribution is mandatory: P0 20%-25%, P1 35%-40%, P2 35%-40% (integer rounding is allowed only for sets below 20 cases). Missing a level, exceeding a range, or changing priority between test point and case fails case review and `validate_case_design.py`; review scores cannot waive it. Read references/case-design.md and references/review-standard.md before assigning or approving priorities.
- Prefer stable execution: verify environment gates (login state, permissions, API reachability) immediately before the first business attempt instead of relying on an earlier probe. When login state is refreshed, every API/data-factory Authorization header must be rebuilt from the current project's new `storage_state`; saved probe/template files may provide request shape but must not provide a reusable token. If UI access works while setup APIs return 401/403, treat stale or divergent authentication as the first diagnosis and refresh the setup channel before marking cases blocked. For login-state capture behind Aliyun silent captcha, prefer a headed real Chrome profile (`channel: 'chrome'` + anti-automation flags) — the silent captcha usually passes automatically and the whole login is hands-free; do not assume manual intervention is required before trying it (see references/execution-playbook.md §1.1).
- Browser launch mode must come from the project framework binding, then `builtin_framework/config.yaml`, with an explicit per-run environment override only when requested. Never hard-code `headless` in a project executor. Copy the resolved browser, mode, and config source into the execution plan, result metadata, and every evidence manifest; mismatches fail the machine gate.
- Use a three-channel execution model: deterministic scripts as the main channel (repeatable, batch/regression friendly), Playwright MCP as the exploration/troubleshooting channel (selector discovery, captchas, unexpected dialogs, failure triage), and API direct-call for prerequisite construction or auxiliary observations allowed by the contract. An `interface: ui` core action cannot be replaced by API success; if the UI core action remains unavailable, mark the case blocked. Keep UI defects separate from business-function defects.
- **Core UI verification, flexible data construction (2026-08-25 Codex comparison lesson)**: build prerequisite data through the most stable available construction channel for the project (API or UI fallback as needed); the formal testcase steps stay business-only. Probe system shapes with read-only endpoints before writing create parameters and never blind-guess parameter formats. When an image control supports both existing-library selection and upload, prefer selecting a current-project image; if upload is required, prepare a project-specific image asset first. UI (channel A) performs the behavior under test: field input/rejection, list-search visibility, edit-page echo, page load, H5 order/pay flows. API may establish baselines and verify side effects but may not perform the field-validation core action. UI interaction failures are "工具定位", never mislabeled "数据工厂". See references/browser-execution.md.
- Harvest execution lessons: after each execution round, fold newly discovered generic pitfalls (selectors, modals, new windows, login expiry, API fallback patterns) back into the workflow references so the next project does not repeat them.
- Treat code review and API contract testing as input-driven optional tracks: skip a track whose required input is missing and record the reason. Functional case design/execution remains core when a runnable UI environment exists, and failed core gates stop progression.
- Optional-input skips do not relax the core gates: missing code skips code review and missing API docs skip contract testing, but functional case design, functional execution, evidence, backfill, and artifact validation remain required when the user supplied a runnable UI environment.

## Deliverable Rules

- `06_final_test_cases.yaml` is the only allowed source for execution, template generation, backfill, and report counts. Initial/aligned/scenario artifacts are analysis inputs only.
- In `case_normalization` mode, `03_existing_cases_import.yaml` is also analysis input only. Preserve its source traceability through review, but never use it instead of `06_final_test_cases.yaml` for execution or reporting.
- A full delivery is incomplete unless `07_case_design_gate.json`, `10_execution_plan_gate.json`, `12_execution_gate.json`, and `19_delivery_gate.json` all have `status: pass`. Business test failures may remain in results; semantic/structural/evidence gate failures may not be waived by a prose review score.
- For generation/review-only runs, `07_case_design_gate.json` plus the review artifacts and `08_测试用例_模板版.xlsx` are the stop point unless the user explicitly asks to continue into execution.
- Use the templates under `assets/templates/` whenever the user asks for concrete output files.
- When the requested scope includes case generation or review, always generate a non-empty testcase XLSX from the gated final source. If the user provided an `xlsx` template, use it; otherwise generate the workflow's default seven-column workbook: `用例ID / 功能集合 / 用例名称 / 优先级 / 前置条件 / 执行步骤 / 预期结果`. Markdown or YAML cannot replace this deliverable. If the requested scope is execution-only, reuse an existing gated template workbook when present; otherwise generate one from the gated final source as part of execution preparation.
- Keep IDs stable across PRD items, cases, reviews, execution results, and defect records.
- **Step 6 (case review) must output a standalone case-review scoring document** (11-dimension per-case scores + dimension summary + veto check), generated from `assets/templates/test-case-review.md`, not only a prose review conclusion.
- Step 6 must also include the priority portfolio audit: P0/P1/P2 counts and percentages, out-of-range cases, per-case rationale checks, and test-point/final-case priority consistency. Priority policy failure is a veto and the review conclusion cannot be `pass`.
- **Step 11/12 backfill hard rules**: (1) the backfill generator must read the full result source that keeps `attempts`/`semantic_contract_sha256`/`execution_trace`/`observations`/`produced_data`, never a stripped summary; (2) the "actual result" column must be the produced business data formatted as readable text (order no / amount / goods name / prompt / no-mutation evidence), the status column keeps pass/fail only; (3) run a self-check before delivery: actual-result column has zero blanks and contains no "第x遍"-style status strings.
- **Step 11/12 evidence rules**: every executed UI case saves a key-evidence screenshot named by case ID (`TC-SP-002.png`) under `artifacts/screenshots/`; the screenshot and manifest must bind the actual assertion moment, file SHA-256, browser, target, semantic keys, verified text, and content anchors. API cases and API-sourced observations use independent `evidence_refs` to request/response or logs and must not fabricate a UI screenshot. Batch UI scripts must include a per-case screenshot helper (see references/execution-playbook.md "截图留证").
- Step 12 must output `23_正式测试报告.docx`; Markdown may be retained as the auditable source, while Allure and execution YAML cannot replace the Word report. The report does not repeat per-case summaries because the backfilled testcase workbook is the detail source.
- 变化类证据为强制项：编辑、删除、选择/取消、重新上传、合并、添加、提交或状态流转等会改变页面/业务状态的用例，必须在每个 attempt 保留独立 before/after 截图并生成 `change_comparison`（前后值/状态、changed、comparison_verified）；最终 canonical 截图从选中 attempt 的 after 截图复制。任一前后证据缺失或无法证明差异时，最多判定为 blocked，不得判 passed。manifest 的 `phase: before` 必须绑定 before_state/前值文本，`phase: after` 必须绑定 after_state/后值文本，并以实际断言值或字段标签作为 `content_anchors`；不得用 after 摘要冒充 before 证据。
- If the user provides a real project PRD, adapt the templates but preserve the field names unless the user asks to change the schema.
- If code-reading output conflicts with PRD, treat PRD as the source of truth and mark code findings as implementation hints, not test requirements.
- If browser tooling is unavailable, still generate the execution plan and a clearly labeled draft report skeleton, and mark execution as pending. A draft skeleton is not `23_正式测试报告.docx` and cannot be declared formally delivered until all four gates pass.
- Prefer the builtin framework under `builtin_framework/` as the default executor for steps 10 and 11. Only use an external framework as an optional compatibility path.
